## 1. 試験の前提

### 1-1. 構成上の読み替え

本システムはサーバを持たず、利用者のブラウザ1つの中で完結する（基本設計書 1-1）。
観点表の用語は次のとおり読み替えて適用する。**読み替えの結果、試験対象が消えるわけではない**——
外部との境界（CDN・ブラウザAPI・URL・CSV・カメラ等）がそのまま「連携先」になる。

| 観点表の用語 | 本システムでの該当 |
|---|---|
| 連携先システム | CDN（jsQR）／フォント配布元（Jost）／ブラウザAPI（IndexedDB・カメラ・クリップボード）／CSV を開く表計算ソフト／URL を開く外部ブラウザ |
| 連携先ダウン | CDN 不達・フォント不達・カメラ拒否／非搭載・保存機能が使えない・ストレージ容量枯渇 |
| タイムアウト | CDN の低速応答（遅延読込が返らない） |
| 不正データ | URL パラメータの改変・利用者入力（XSS・CSV 数式・メール表記ゆれ）・境界値（定員・締切時刻・20MB） |

### 1-2. 試験環境

| 項目 | 内容 |
|---|---|
| 起動 | `python3 -m http.server 8010` → `http://127.0.0.1:8010/`（`file://` 不可） |
| ブラウザ | Chrome 最新（主）。参加者ビューのスマホ幅確認は iOS Safari または F12 のスマホ表示 |
| QR の読み取り | カメラ付き端末＋**スマホ等の第2の端末**（1台では自分の画面を自機カメラで読めない） |
| 通信異常の再現 | F12 → Network の「Offline」「Block request URL」「Slow 3G」 |
| 自動試験 | `node tests/guard.js` / `node tests/smoke.js`。CI（`.github/workflows/test.yml`）が push と pull request で実行 |

### 1-3. 試験データ

| 項目 | 内容 |
|---|---|
| デモデータ | 設定画面から投入。イベント40件・参加者24人・申込約220件 |
| 使い方 | **必ず「初期化→投入」の順で使う**（初期化せず続けて投入すると申込などが重複する） |
| ログイン | 田中 太郎 `abc@example.com` / `abc123`（パスワードを持つ唯一の人物） |
| 名簿の解除 | `admin` |

### 1-4. 自動と手動の区分（各項目の「区分」列）

| 区分 | 意味 | 件数 |
|---|---|---|
| **自動** | 自動テストが毎回検証しており、手動実施は不要（結果欄に「自動」と記入する） | 11 |
| **自動＋手動** | 動き（判定・保存・表示の中身）は自動テストで検証済み。**画面での見え方・実機での操作感だけ**を確認する | 97 |
| **手動** | 自動テストでは確認できないため、**必ず人が実施する**（カメラ・通信遮断・実機の操作感・表計算での実開きなど） | 41 |

合計 **149 項目**。区分は `tests/smoke.js` の各テストと1行ずつ突合して決めている（推測で「自動」にはしない）。

> **実施記録（Excel）との対応**：`結合試験項目一覧.xlsx` の備考欄は **「自動」「手動」の2値**で運用している。
> 本書の**「自動＋手動」は Excel では「自動」と記録する**（動きは自動テストが担保しており、
> 残るのは画面の見え方の確認だけなので、実施記録上は自動扱いで足りる）。
> **「手動」は両方で一致している**（41件）。本書が3値を保つのは、手動で何を見ればよいかを
> 区別できるようにするため。

## 2. IF一覧（連携網羅性の基準線）

詳細設計書 2-3（区画と依存関係）・3章（モジュール定義）・4章（処理フロー）、および基本設計書 1-4（通信の発生場面）から抽出した。
**本システムにおける「IF」= モジュール間の呼び出し境界（内部IF）と、ブラウザ／外部世界との境界（外部IF）。**

### 2-1. 内部IF（モジュール間）

| ID | 連携（呼び出し元 → 先） | 内容 |
|---|---|---|
| IF-I01 | 画面 → `Repo` | ストア別データアクセス（events / persons / applications / savedTokens / messages / tasks / readStates / manuals / files） |
| IF-I02 | `Repo` → `DB` | Promise ラップ・`bulkPut`（複数ストア1トランザクション）・`reset` |
| IF-I03 | 画面 → `AppSvc` | `apply` / `cancel` / `setCheckin` / `editApplicant` / `validate`。**主催者側と参加者側が同じ関数を呼ぶ**（F-25） |
| IF-I04 | `AppSvc` → `Domain` | `timing` / `remaining` / `usedSeats` / `isValidApp`（申込可否の判定） |
| IF-I05 | 画面 → `Domain` | `timing` / `applyButtonLabel` / `nearlyFull` / `taskSummary` / `taskOverdue` / `staleDraft`（表示用の都度算出） |
| IF-I06 | 画面 → `Util` | `esc` / `fmtRange` / `markdown` / `csvCell` / `buildCsv` / `normalize` / `copy` / `loadScript` |
| IF-I07 | 画面 → `FB` | `toast`（完了）・`error`（システムエラー）・`confirmModal`（取り消せない操作の確認） |
| IF-I08 | `Participant` / `App` → `Auth` → `Repo` | `login` / `logout` / `person`（マイ申込一覧のログイン。F-107） |
| IF-I09 | `App` ⇄ 画面 | `render` の呼び出し／画面からの遷移要求／`renderContent` の描画直列化／`applyView` の viewport 切替 |
| IF-I10 | `EventDetail` → `Ops` / `Tasks` / `Manual` / `Files` | S-4 サブタブの委譲描画 |
| IF-I11 | `Settings` → `Seed` → `Repo` | デモデータ投入・初期化 |

### 2-2. 外部IF（ブラウザ・外部世界との境界）

| ID | 連携 | 内容 |
|---|---|---|
| IF-E01 | ブラウザ ⇄ IndexedDB | 接続・`onupgradeneeded`（v1→v5 の create-if-missing 移行）・トランザクション |
| IF-E02 | `Util.loadScript` → CDN | `jsQR` の遅延読込。**実行時に外部コードを取得する唯一の箇所**（リスク R-01） |
| IF-E03 | `@font-face` → フォント配布元 | Jost（英数字）の取得。失敗時はシステム書体で表示継続 |
| IF-E04 | URL パラメータ → `App.routeFromUrl` | `?ticket=` / `?event=` / `?preview=`。**解析の直後・処理より先に**URLを戻す |
| IF-E05 | CSV 出力 → 表計算ソフト | BOM 付き CRLF・数式無害化（F-49b） |
| IF-E06 | `Util.copy` → クリップボードAPI | 共有URL・投稿文のコピー |
| IF-E07 | `getUserMedia` → カメラ | QR 読み取りによる当日受付（受付は1台のみ） |
| IF-E08 | 外部リンク | X / LINE 共有・会場の地図・会社ロゴ。`rel="noopener"` |
| IF-E09 | QR 生成（同梱ライブラリ） | 確認URL のトークンを QR 画像化（生成は同梱・読取は E02/E07） |
| IF-E10 | ファイル入力（`File` / `Blob`）→ IndexedDB | Blob をそのまま保存（`FileReader` 禁止）。1ファイル 20MB まで |

## 6. エビデンスの記録

### 6-1. 記録の原則

- **試験1件につきエビデンス1件以上。** Excel の結果欄に「○」を書くだけでは完了とみなさない
- 画面の確認は**スクリーンショット**、データの確認は **F12 → Application → IndexedDB のスクリーンショット**、自動試験は**実行ログ**を残す
- CSV・ダウンロード物は**成果物そのもの**を保存する

### 6-2. 保存場所と命名規則

| 種別 | 保存先・命名 |
|---|---|
| スクリーンショット | `evidence/<項目番号>_<YYYYMMDD>_<連番>.png`（例：`evidence/3-3-1_20260729_01.png`） |
| 自動試験ログ | `node tests/smoke.js > evidence/smoke_<YYYYMMDD>.log 2>&1`（`guard.js` も同様） |
| CI の記録 | GitHub Actions の実行 URL を Excel の履歴欄に転記 |
| 出力ファイル | `evidence/<項目番号>_<YYYYMMDD>_<元のファイル名>` |

### 6-3. 実施記録の様式

**実施記録は `docs/結合試験項目一覧.xlsx` に記入する**（担当者／日付／結果／履歴／備考の各列）。

| 列 | 記入内容 |
|---|---|
| 担当者・日付 | 実施した人と日付。自動テストで済む行は「自動テスト」と実行日 |
| 結果 | ○ / ×（× のときは履歴欄に事象、備考欄に不具合票No） |
| 履歴 | 引っかかった点・確認できなかった理由・CI の実行URL |

- **× の場合**は必ず不具合票 No を記入し、7章の回帰試験記録に接続する
- 区分が「自動」の行は、CI が成功していれば結果欄に「○」＋履歴欄に「guard+smoke 150件成功」と記入してよい

## 7. 回帰試験の実施記録

### 7-1. 運用ルール

1. 不具合を修正したら**修正コミットを push する**。CI が `guard.js` と `smoke.js` の全件を自動で再実行する——これを回帰試験の自動実施とみなし、**CI の実行 URL を記録する**
2. 自動テストでカバーされない項目（区分が「手動」の行、特にカメラ・通信遮断・表計算での実開き）は、**修正の影響範囲に該当する項目番号を手動で再実施**する
3. 影響範囲の判定には詳細設計書 13章（変更時のチェックリスト）と 11章（壊れやすい箇所）を用いる。壊れやすい箇所に触れた修正は、該当する項目番号を必ず再実施する
4. 記録は下表に1不具合1行で残す（DES-085 への紐づけは対象外 / 0章の注記）

## 8. レビューの手引き（網羅性・IF境界の妥当性）

**観点表の5観点のうち、仕様書の段階で判定できるのは上3つ。** 下2つ（エビデンス・回帰記録）は「記録できる様式と手順が定義されているか」を見る。

### 8-1. 連携網羅性の見方（機械的にやる）

1. 本書を見ずに、詳細設計書 2-3（依存関係表）・3章（メソッド定義）・4章（シーケンス図の矢印）から**自分で IF を書き出す**
2. 書き出した IF と 2章の IF一覧を突き合わせ、**片方にしかないものを列挙**する
3. 5章のマトリクスで**空欄の行**を探す（空欄＝試験漏れの候補）
4. シーケンス図（詳細 4-1〜4-4）の**矢印1本1本**に対応する項目があるか指でなぞる

### 8-2. 異常系の充足の見方

- 外部IF（IF-E01〜E10）ごとに「ダウン・タイムアウト・不正データ」の3分類を数える。**該当し得るのに0件の分類**があれば指摘する（該当しない場合は 1-1 の読み替え表で説明できること）
- 4-1節の分類ごとの件数と、3章の該当行の条件欄が一致しているか確認する

### 8-3. IF境界の妥当性の見方（境界値の5点セット）

各 IF の引数・入力について、次が試験されているか確認する。

| 種類 | 見る点 | 本システムでの例（項目番号） |
|---|---|---|
| 件数 | 0件・1件・上限ちょうど・上限+1 | 残席1→0（4-3-5）・20MBちょうど/超（3-12-3）・申込0件のイベント |
| 時刻 | 境界の直前・ちょうど・直後 | 締切 23:59／翌 0:00（4-3-10）・受付開始 0:00 |
| 文字列 | 空・表記ゆれ・危険文字 | メール大文字空白（4-3-8）・XSS（6-3-6）・CSV 数式（3-6-2） |
| 検証の責務 | 誰が検証しどう伝えるか | `AppSvc` が throw し画面が表示（詳細 10章）。**両側で二重検証していないか／どちらも検証していない引数が無いか** |
| 順序 | 複数条件の同時成立 | 中止かつ満席（4-3-7）・時期の評価順（4-2-2） |
