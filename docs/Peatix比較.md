# Peatix との機能比較

作成日：2026年7月28日

要件の骨格は、既存サービスである Peatix の主催者向け機能を調査して組み立てた。本書は
**「Peatix にあって本システムに無いもの」と「その逆」を1枚にまとめたもの**である。

内容は `引き継ぎ書.md` の第5章・第9章を統合したもの。**判断の理由の正典は
`要件定義書.md` である**（CLAUDE.md の定めによる）。本書は要件定義書の内容を Peatix との
対比の形に整理した派生文書であり、**齟齬がある場合は要件定義書を優先する。新たな判断は
要件定義書本文に直接反映し、本書はそれを参照する**（二重管理に戻さない）。
設計判断の背景・経緯は引き継ぎ書を参照。

> **前提の変更（2026-07-28）— 社外向けイベント専用にした。**
> 当初は社内向け専用として設計していたが、**扱うのは社外向けイベントのみ**（取引先・同業他社・
> 一般の方が申込む）へ全面的に反転した（F-98）。これにより **Peatix との距離が縮まる**——
> Peatix も社外向けの集客イベントを扱うサービスだからである。
> 本書の「社内向けだから不要」という論法は使えなくなるため、1-1 の理由を書き換えた。
> 一方、**マルチテナントでない**点（1-7）は変わらない。

## この文書の位置づけ

引き継ぎ書 4-1 は、サーバが無いことによる制約について次の方針を置いている。

> 実装できないことを隠すのではなく、構造として示すのが本プロジェクトの評価軸のひとつ。

「なぜ無いのか」の説明は**区分ごとに理由が違う**。混同すると、意図して外したものまで
検討漏れに見える。本書を区分に分けているのはそのためである。

> **改訂（2026-07-28）— 区分の粒度を見直した。**
> 旧版は「技術的に不可能（サーバが必要）」という1区分に、実際には性質の異なる2つを
> まとめていた。すなわち **①サーバが無いと原理的に不可能なもの** と、
> **②サーバ無しでも代替が成立するもの** である。両者が同じ欄に並んでいると、
> 「制約を構造として示した」という主張がかえって成立しにくくなる。できることまで
> 不可能の側に寄せているように読めるためである。
>
> 本改訂で ① と ② を分離し、さらに **③ 検討していなかったもの** を 1-5 として
> 明示した。③ を隠さないことが、①②の説明の信頼度を担保する。

## 1. Peatix にあって本システムに無いもの

### 1-1. 構造的に不要 — 本システムの形では、そもそも発生しない

| 機能 | なぜ不要か |
|---|---|
| ウィジェット埋め込み | イベントページが自社側にあるため、外部プラットフォームへの橋渡しが発生しない |
| リンク先URLの変更 | 同上 |
| 有料集客サービス | 金銭を扱わないため（1-7 の対象領域外）。**社外向けに転換しても理由は変わらない**——集客の必要はあるが、有料広告の購入は本システムの領域外 |
| カテゴリー | 参加者側にイベント検索が無いため、絞り込む画面が存在しない。**社外向けでも同じ**——公開ページには共有URLから直接到達する |
| カスタムURL | 同上 |

### 1-2. ① 原理的に不可能 — サーバが無いと成立しない

**この区分が、成果物の説明で最も価値を持つ。** 単一HTML・サーバなしという制約から
原理的に導かれるものであり、実装で回避しようとしないこと（引き継ぎ書 4-1）。

| 機能 | 不可能な理由 |
|---|---|
| メールの実送信（申込確認・リマインド・中止通知） | APIキーをHTMLに書けない。定時実行（cron）も持てない |
| SNS自動投稿 | 同上 |
| SEO | クローラが到達できる公開ホスティングが要る。**ホスティング先は本課題の範囲外**（成果物は単一HTMLで、ローカルHTTPサーバ経由での起動を前提とする / 3-2） |
| イベントごとの OGP 出し分け | `<head>` は静的で、`?event=` に応じて `og:` を切り替えるにはサーバ側のレンダリングが要る |
| プレビューの他者共有 | 自己確認は `?preview=` で実装済み（F-07）だが、**他人に見せるには公開URLが要る**。`shareUrl` が組むのは `location.origin` 配下のURLで、外部からは到達できない |
| 他端末での閲覧数計測 | 集計するサーバが無い |
| 複数端末での同時受付（アシスタントモード相当） | 端末間でチェックイン状態を共有できない |
| 参加者が別端末で申込を確認する | トークンがブラウザ内にしか無い（3-3「F-56の限界」） |

### 1-3. ② サーバ無しでも代替が成立するもの

**「不可能」と混ぜてはいけない区分。** 完全な代替ではないが、目的の相当部分は満たせる。

| Peatix の機能 | 本システムの代替 | 状態 |
|---|---|---|
| SNSへの自動投稿 | 投稿文を生成し、X／LINE の共有画面を開く手動ボタン | 実装済み（F-11〜F-15） |
| 会場地図の埋め込み | 住所から外部地図サービスを開くリンク | 実装済み（F-68） |
| 主催者から参加者へのメッセージ／変更通知メール | **お知らせ**。公開ページとマイ申込に掲示する。Peatix のメッセージもメール通知と受信箱の2層構成であり、後者に相当する層はサーバ無しでも成立する | **実装済み**（2026-07-28） |
| 販売開始日時 | **受付開始日**（`applyStartAt`）。未設定なら公開と同時に受付開始 | **実装済み**（2026-07-28 / F-45b） |
| QRコードでの受付 | `getUserMedia` + CDN の jsQR でカメラ読み取り。参加者のマイ申込にQRを表示する | **実装済み**（2026-07-28 / F-95。1台のみ） |
| 申込推移のグラフ | `appliedAt` から日次の推移を描く。閲覧数の計測（サーバが必要）とは別物 | **実装済み**（2026-07-28 / F-96） |
| オンライン開催の視聴URLを申込者限定で表示 | マイ申込にのみ表示する。公開ページには出さない | **実装済み**（2026-07-28 / F-93） |
| 固定の OGP タグ | `<head>` に静的な `og:title` / `og:description` を書くこと自体はサーバ無しでもできる | 未実装（イベント単位で出し分けられないため、現状は効果が薄い） |

### 1-4. ①の波及 — 端末間のデータ共有

サーバが無いことから**端末間のデータ共有そのものが不可能**である。影響は個別機能に
とどまらない。

> **社外向けにおいて、これは「参加者は定義上いつも別端末」を意味する。**
> 要件定義書 1-2 は参加者を「不特定多数の社外の方」と定義しており、社内向け時代のように
> 「同じ社内ネットワークの、同じ端末を触りうる相手」ではない。
> **つまり本システムは、研修課題として単一ブラウザ内で主催者と参加者の両方を演じる前提で
> 作られている。** 実運用ではこの前提が最初に崩れる。
> 制約の内容は転換前と変わらないが、**転換によって「実用に耐えない度合い」は上がった。**
> ここを曖昧にしないために明記する。

| できないこと | 本システムでの扱い |
|---|---|
| 主催者と参加者が別端末で使う | **実運用では常にそうなる。** 本システムは同一ブラウザ内の役割切替で「代用」しており、これは実装ではなく**デモのための演出**である |
| 参加者が別端末で申込を確認する | **社外の参加者にとっては、これが通常の経路。** 手段が無い（要件定義書 3-3「F-56の限界」）。確認トークンはブラウザ内に保存され、主催者側からの再発行も持たない。**申込した端末を変えた時点で確認できなくなる** |
| 運営メンバー間での共有 | 実態は一人（同一ブラウザ）での管理。運営スレッド・Q&A・タスクは複数人での共有管理を想定した設計だが、同期はサーバ導入時まで不可 |
| 締切を過ぎたら受付終了へ自動変更 | 定時実行が無いため、時期は保存せず都度算出する（4-3）。結果として自動変更の処理自体が不要になっている |

### 1-5. ③ 検討していなかったもの — 未検討であることを明示する

**旧版の4区分のどこにも記載が無かった項目。** 意図的除外でも技術的不可能でもなく、
単に検討が漏れていた。隠すと①②の説明まで疑わしくなるため、ここに列挙する。

いずれも**サーバ無しで実装可能**であり、「できない」ではなく「やっていなかった」ものだった。
**2026-07-28 に a・c・e・f・h を実装し、i・j は判断を明記した。**

| # | 機能 | 内容と、本システムでの必要性 | 現在 |
|---|---|---|---|
| a | **申込フォームのカスタム質問** | Peatix は主催者が質問項目を作成でき、回答をCSVで取得できる。旧実装は氏名・カナ・メールの3項目固定だった。社外向けでは「会社名」「役職」「参加方法」「知ったきっかけ」が要る。**所属会社を `persons` ではなくここで取得している**（所属は時期で変わるため） | ✅ F-91 |
| c | **開催形式（オンライン／ハイブリッド）** | 旧データ設計は `venueName` / `venueAddress` のみで、開催形式の概念が無かった。Teams/Zoom の URL を申込者だけに見せる要求は普通に発生する | ✅ F-93 |
| e | **イベントの複製** | `groupId` / `copiedFromId` を持ちながら対応機能が無く、**シードが埋めるだけの死にフィールド**だった。定例のセミナーやウェビナーは複製の主戦場 | ✅ F-94 |
| f | **QRコードでの受付** | 旧実装は氏名検索＋行内ボタンのみ。要件定義書 1-2 が「1イベントあたり参加者数百人」を想定と明記している以上、氏名検索だけの受付は規模と釣り合わない | ✅ F-95（1台のみ） |
| h | **申込推移の可視化** | ダッシュボードは「今週の申込数」という単一の数値のみだった | ✅ F-96 |
| i | **パスワード保護イベント** | Peatix は公開範囲が3段（一般公開／限定公開／パスワード保護）、本システムは2段。**クライアント側のパスワードはHTMLを読めば突破できるため、秘匿の役に立たない。** 限定公開のランダムURLのほうが実効性が高い。よって採用しない | ⛔ 除外（理由を明記） |

| j | **キャンセル待ち** | 定員あり・無料のイベントで要望が出やすい。**採用しないのは、繰り上げ通知の手段が無いため。** メール送信ができない以上、繰り上がっても本人が気づけず、席だけ確保されて空振りする。通知手段（＝サーバ）が入るまで意味を持たない | ⛔ 除外（理由を明記） |
| k | **多言語対応（英語）** | 「同業他社・一般」を対象にするなら英語需要は現実的に発生する。**1-1〜1-7 のどこにも言及が無かった。** 文言の外部化は単一HTMLでも可能なので②に相当するが、全画面の文言を分離する作業量が大きい。**2026-07-29 に「一旦考えない」と決定**（研修の範囲外とする） | ⛔ 見送り（決定済み） |
| l | **参加者のログイン（会員機能）** | Peatix は参加者にアカウントがあり、どの端末からでも自分の申込を見られる。本システムは端末に保存した控え（`savedTokens`）だけだったため、**同じブラウザを使った別人の申込まで一覧に並んでいた。** マイ申込の一覧にログインを足して解消した（F-107）。ただし**サーバが無いのでパスワードは IndexedDB に平文で入り、秘匿ではなく操作の抑止にとどまる**（F-107b）。別端末からの復帰は依然できない（1-6） | ✅ F-107（限界を明記） |

> **参加者名簿のパスワード（F-101）・参加者ログイン（F-107）との関係。** どちらもパスワードを
> 使うが、i の判断と矛盾しない。**これらは秘匿ではなく操作の抑止**（肩越しの覗き見・誤操作の防止、
> および他人の申込一覧を開かせないこと）として位置づけており、画面にもその限界を明記している。
> イベントのパスワード保護は「第三者から秘匿する」ことが目的であり、それはクライアント側では
> 達成できない。目的が違う。
> （この注記は以前 i と j の間にあり、表を分断していたため末尾へ移した。）

> **f の分類について。** 旧版は「QRコードでの受付」と「複数端末での同時受付」を
> まとめて意図的除外に置いていた。前者は `getUserMedia` で単一HTMLでも動くので ②、
> 後者は端末間共有が要るので ① である。粒度が粗かった。**現在は前者のみ実装している。**

### 1-6. 意図的に除外 — できるが、やらないと決めた

1-5 が「③を隠さないことが①②の説明の信頼度を担保する」として全項目に理由を書いた以上、
**この区分も同じ水準で書く。** 項目を並べただけでは、旧版のまま放置されていると読まれる。

> **削除した2件（2026-07-28）。** 「QRコードでの受付」は F-95 で実装済み（1台のみ。
> 複数端末での同時受付は 1-2 の①のまま）。「プレビュー共有」は**①へ移した**——
> 自己確認は `?preview=` で実装済み（F-07）だが、他人に見せるには公開URLが要るため、
> 意図的除外ではなく原理的に不可能な側である。どちらも 1-6 に残すと 1-5 f や
> 設定画面の実装区分一覧と矛盾する。

| 機能 | 除外の理由 | 社外向け転換後の扱い |
|---|---|---|
| フォロワー機構 | 再来訪導線は主催者側からの働きかけで足りる。**参加者名簿 S-10（F-92）が過去の参加者を横断で保持しており、②の代替が成立している**（実際に送る手段はサーバ導入後） | 転換後も維持 |
| チケット譲渡 | 「行けなくなったので同僚が代わりに」は社外向けでも起きる。**採用しないのは、譲渡先の本人確認ができないため**（F-105）。申込内容の修正（F-26）で氏名を書き換える運用で代替する | **転換後に再判断し、維持** |
| 代理申込 | 「弊社から3名参加します」は社外向けで一般的。**採用しないのは、F-16 が申込者本人のメールアドレスを名寄せキーにしており（4-5）、代理申込では同一アドレスに複数人がぶら下がって名簿（F-92）が壊れるため**（F-104）。人数分を個別に申込む運用とする | **転換後に再判断し、維持** |
| 抽選 | 定員超過時の標準的な手段。**採用しないのは、当落の通知手段が無いため**（F-106）。キャンセル待ち（1-5 j）と同じ理由で、通知（＝サーバ）が入るまで意味を持たない | **転換後に再判断し、維持** |
| 定期開催 | **F-94 の複製が代替になっている。** 「製品活用セミナー 第1〜5回」のような定例は、前回を複製して日付だけ変える運用で回る。繰り返しルールを持つより単純 | 転換後も維持（②で代替済み） |
| レスポンシブ対応 | **参加者側は実装済み（F-81b / 2026-07-29）。** 社外の参加者の端末は選べないので、F-81「PC幅のみ」の前提が成り立たなかった。`viewport` をビューごとに切り替え、参加者ビューだけ 640px 以下に対応する。**主催者側は対応しない**——運営は端末を統制できるため | 参加者側は解消／主催者側は維持 |

これに加えて、次の2つがある。

**参加者側の発見機能**（イベント検索・グループページ・アクティビティ投稿）。
参加者側を「体験を提供する画面」ではなく**「管理側にデータを供給する入力口」**と
位置づけたため（引き継ぎ書 4-9）。参加者向けは公開ページ・申込・完了・マイ申込の
4画面のみとする。

**チケット制**（2026-07-27 の設計変更で追加）。Peatix は無料イベントでも「無料チケット
を買う」という操作を要求するが、無料イベントでこの摩擦は不要と判断した。申込は「申込」
に一本化し、`ticketTypes` ストアごと廃止している。これに伴い**複数チケット種別・価格
設定・枠ごとの定員**も持たない。定員はイベント全体で1つ（`events.capacity`）。

### 1-7. 対象領域外

決済・手数料・入金・返金・請求書、ライブ配信。金銭は前提（要件定義書 1-2）から外している。

加えて、**マルチテナントではない**。Peatix は誰でも主催者になれるプラットフォームだが、
本システムは自社のみを想定する（自社が社外向けイベントを開催するのであって、他社が主催者に
なるわけではない）。参加者リストの扱いなど、マルチテナント固有の制約を負わない点はここに由来する。

## 2. 本システム側の作り

> **本章の位置づけを変更した（2026-07-28）。**
> 以前は「Peatix にはこの制約があるが本システムには無い」という**優位性の主張**だった。
> しかし前提にしていた Peatix 側の3点の制約に**裏付けが取れなかった**（4章）。
> 裏付けのない比較を差別化の根拠にはできないので、**主張を取り下げ、
> 「本システムがどう作られているか」の記述に改めた。**
>
> 本プロジェクトの目標は **Peatix の機能をある程度模倣できていること**であり、
> Peatix より優れていることを示すことではない。

### 2-1. 参加者データの扱い

| 項目 | 本システム |
|---|---|
| 参加者リスト | 氏名・カナ・メールアドレスを表示し、CSV にも出力する |
| 保持期間 | **期限を設けない。** 過去の参加履歴を次回に活かすため |
| 名寄せ | 申込のたびにメールアドレス（trim + 小文字化）で同一人物にまとめる |
| 横断参照 | 参加者名簿 S-10（F-92）で、同一人物の参加履歴・来場回数・最終申込日を引ける |

画面を持たない `person` エンティティを当初から保持しているのは、後から追加すると
全 `applications` の付け替えが必要になるためである（引き継ぎ書 4-5）。

### 2-2. 申込内容の変更

金銭を扱わないため、購入済み商品としての同一性を保つ必要がない。
そのため申込後でもイベント名や内容を変更できる（F-01）。

### 2-3. データアクセスの抽象化

外部システムとの連携機能は持たない（HTTP API が無い）。
ただしデータの読み書きを Repository 層に集約し、全メソッドを Promise で定義してある。
サーバを導入する際に、業務ロジックを変えずに API 実装へ差し替えられる状態を保つため
（引き継ぎ書 4-2）。**これは本システム側の設計の話であり、Peatix の仕様に依存しない。**
