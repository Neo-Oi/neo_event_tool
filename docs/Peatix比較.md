# Peatix との機能比較

作成日：2026年7月28日

要件の骨格は、既存サービスである Peatix の主催者向け機能を調査して組み立てた。本書は
**「Peatix にあって本システムに無いもの」と「その逆」を1枚にまとめたもの**である。

内容は `引き継ぎ書.md` の第5章（実装しないものと、その4区分）と第9章（Peatix との関係）
を統合し、2026-07-27 の設計変更（チケット制の廃止）を反映したもの。**判断の理由は
引き継ぎ書が正典であり、齟齬がある場合はそちらを優先する。**

> **前提の変更（2026-07-28）— 社外向けイベントを主とする。**
> 当初は社内向け専用として設計していたが、社外向けイベント（取引先・同業他社・一般の方が
> 申込む）を主に扱う方針へ変更した（F-98）。これにより **Peatix との距離が縮まる**——
> Peatix も社外向けの集客イベントを扱うサービスだからである。
> 本書の「社内向けだから不要」という論法は使えなくなるため、1-1 の理由を書き換えた。
> 一方、**マルチテナントでない**点（1-7）は変わらず、2 章の差別化の根拠であり続ける。

## この文書の位置づけ

引き継ぎ書 4-1 は、サーバが無いことによる制約について次の方針を置いている。

> 実装できないことを隠すのではなく、構造として示すのが本プロジェクトの評価軸のひとつ。

「なぜ無いのか」の説明は**区分ごとに理由が違う**。混同すると、意図して外したものまで
検討漏れに見える。本書を区分に分けているのはそのためである。

> **改訂（2026-07-28）— 区分の粒度を見直した。**
> 旧版は「技術的に不可能（サーバが必要）」という1区分に、実際には性質の異なる2つを
> まとめていた。すなわち **①サーバが無いと原理的に不可能なもの** と、
> **②サーバ無しでも代替が成立するもの** である。両者が同じ欄に並んでいると、
> 「制約を構造として示した」という主張がかえって成立しにくくなる。できることまで
> 不可能の側に寄せているように読めるためである。
>
> 本改訂で ① と ② を分離し、さらに **③ 検討していなかったもの** を 1-5 として
> 明示した。③ を隠さないことが、①②の説明の信頼度を担保する。

## 1. Peatix にあって本システムに無いもの

### 1-1. 構造的に不要 — 本システムの形では、そもそも発生しない

| 機能 | なぜ不要か |
|---|---|
| ウィジェット埋め込み | イベントページが自社側にあるため、外部プラットフォームへの橋渡しが発生しない |
| リンク先URLの変更 | 同上 |
| 有料集客サービス | 金銭を扱わないため（1-7 の対象領域外）。**社外向けに転換しても理由は変わらない**——集客の必要はあるが、有料広告の購入は本システムの領域外 |
| カテゴリー | 参加者側にイベント検索が無いため、絞り込む画面が存在しない。**社外向けでも同じ**——公開ページには共有URLから直接到達する |
| カスタムURL | 同上 |

### 1-2. ① 原理的に不可能 — サーバが無いと成立しない

**この区分が、成果物の説明で最も価値を持つ。** 単一HTML・サーバなしという制約から
原理的に導かれるものであり、実装で回避しようとしないこと（引き継ぎ書 4-1）。

| 機能 | 不可能な理由 |
|---|---|
| メールの実送信（申込確認・リマインド・中止通知） | APIキーをHTMLに書けない。定時実行（cron）も持てない |
| SNS自動投稿 | 同上 |
| SEO・OGP | 公開URLが存在しない |
| 他端末での閲覧数計測 | 集計するサーバが無い |
| 複数端末での同時受付（アシスタントモード相当） | 端末間でチェックイン状態を共有できない |
| 参加者が別端末で申込を確認する | トークンがブラウザ内にしか無い（3-3「F-56の限界」） |

### 1-3. ② サーバ無しでも代替が成立するもの

**「不可能」と混ぜてはいけない区分。** 完全な代替ではないが、目的の相当部分は満たせる。

| Peatix の機能 | 本システムの代替 | 状態 |
|---|---|---|
| SNSへの自動投稿 | 投稿文を生成し、X／LINE の共有画面を開く手動ボタン | 実装済み（F-11〜F-15） |
| 会場地図の埋め込み | 住所から外部地図サービスを開くリンク | 実装済み（F-68） |
| 主催者から参加者へのメッセージ／変更通知メール | **お知らせ**。公開ページとマイ申込に掲示する。Peatix のメッセージもメール通知と受信箱の2層構成であり、後者に相当する層はサーバ無しでも成立する | **実装済み**（2026-07-28） |
| 販売開始日時 | **受付開始日**（`applyStartAt`）。未設定なら公開と同時に受付開始 | **実装済み**（2026-07-28 / F-45b） |
| QRコードでの受付 | `getUserMedia` + CDN の jsQR でカメラ読み取り。参加者のマイ申込にQRを表示する | **実装済み**（2026-07-28 / F-95。1台のみ） |
| 申込推移のグラフ | `appliedAt` から日次の推移を描く。閲覧数の計測（サーバが必要）とは別物 | **実装済み**（2026-07-28 / F-96） |
| オンライン開催の視聴URLを申込者限定で表示 | マイ申込にのみ表示する。公開ページには出さない | **実装済み**（2026-07-28 / F-93） |

### 1-4. ①の波及 — 端末間のデータ共有

サーバが無いことから**端末間のデータ共有そのものが不可能**である。影響は個別機能に
とどまらない。

| できないこと | 本システムでの扱い |
|---|---|
| 主催者と参加者が別端末で使う | 同一ブラウザ内の役割切替で表現する |
| 参加者が別端末で申込を確認する | 手段が無い（要件定義書 3-3「F-56の限界」）。確認トークンはブラウザ内に保存され、主催者側からの再発行も持たない |
| 運営メンバー間での共有 | 実態は一人（同一ブラウザ）での管理。運営スレッド・Q&A・タスクは複数人での共有管理を想定した設計だが、同期はサーバ導入時まで不可 |
| 締切を過ぎたら受付終了へ自動変更 | 定時実行が無いため、時期は保存せず都度算出する（4-3）。結果として自動変更の処理自体が不要になっている |

### 1-5. ③ 検討していなかったもの — 未検討であることを明示する

**旧版の4区分のどこにも記載が無かった項目。** 意図的除外でも技術的不可能でもなく、
単に検討が漏れていた。隠すと①②の説明まで疑わしくなるため、ここに列挙する。

いずれも**サーバ無しで実装可能**であり、「できない」ではなく「やっていなかった」ものだった。
**2026-07-28 に a・c・e・f・h を実装し、i・j は判断を明記した。**

| # | 機能 | 内容と、社内イベントでの必要性 | 現在 |
|---|---|---|---|
| a | **申込フォームのカスタム質問** | Peatix は主催者が質問項目を作成でき、回答をCSVで取得できる。旧実装は氏名・カナ・メールの3項目固定だった。社内イベントこそ「所属部署」「食事アレルギー」「懇親会の参加可否」「現地/オンライン」が要る | ✅ F-91 |
| c | **開催形式（オンライン／ハイブリッド）** | 旧データ設計は `venueName` / `venueAddress` のみで、開催形式の概念が無かった。Teams/Zoom の URL を申込者だけに見せる要求は普通に発生する | ✅ F-93 |
| e | **イベントの複製** | `groupId` / `copiedFromId` を持ちながら対応機能が無く、**シードが埋めるだけの死にフィールド**だった。社内の「毎月の勉強会」は複製の主戦場 | ✅ F-94 |
| f | **QRコードでの受付** | 旧実装は氏名検索＋行内ボタンのみ。要件定義書 1-2 が「1イベントあたり参加者数百人」を想定と明記している以上、氏名検索だけの受付は規模と釣り合わない | ✅ F-95（1台のみ） |
| h | **申込推移の可視化** | ダッシュボードは「今週の申込数」という単一の数値のみだった | ✅ F-96 |
| i | **パスワード保護イベント** | Peatix は公開範囲が3段（一般公開／限定公開／パスワード保護）、本システムは2段。**クライアント側のパスワードはHTMLを読めば突破できるため、秘匿の役に立たない。** 限定公開のランダムURLのほうが実効性が高い。よって採用しない | ⛔ 除外（理由を明記） |
| j | **キャンセル待ち** | 定員あり・無料の社内イベントで要望が出やすい。**採用しないのは、繰り上げ通知の手段が無いため。** メール送信ができない以上、繰り上がっても本人が気づけず、席だけ確保されて空振りする。通知手段（＝サーバ）が入るまで意味を持たない | ⛔ 除外（理由を明記） |

> **f の分類について。** 旧版は「QRコードでの受付」と「複数端末での同時受付」を
> まとめて意図的除外に置いていた。前者は `getUserMedia` で単一HTMLでも動くので ②、
> 後者は端末間共有が要るので ① である。粒度が粗かった。**現在は前者のみ実装している。**

### 1-6. 意図的に除外 — できるが、やらないと決めた

フォロワー機構、QRコードでの受付、チケット譲渡、キャンセル待ち、抽選、代理申込、
定期開催、プレビュー共有、レスポンシブ対応。

これに加えて、次の2つがある。

**参加者側の発見機能**（イベント検索・グループページ・アクティビティ投稿）。
参加者側を「体験を提供する画面」ではなく**「管理側にデータを供給する入力口」**と
位置づけたため（引き継ぎ書 4-9）。参加者向けは公開ページ・申込・完了・マイ申込の
4画面のみとする。

**チケット制**（2026-07-27 の設計変更で追加）。Peatix は無料イベントでも「無料チケット
を買う」という操作を要求するが、社内イベントでこの摩擦は不要と判断した。申込は「申込」
に一本化し、`ticketTypes` ストアごと廃止している。これに伴い**複数チケット種別・価格
設定・枠ごとの定員**も持たない。定員はイベント全体で1つ（`events.capacity`）。

### 1-7. 対象領域外

決済・手数料・入金・返金・請求書、ライブ配信。金銭は前提（要件定義書 1-2）から外している。

加えて、**マルチテナントではない**。Peatix は誰でも主催者になれるプラットフォームだが、
本システムは自社のみを想定する（自社が社外向けイベントを開催するのであって、他社が主催者に
なるわけではない）。この差が 2 章の判断に効いてくる。

## 2. Peatix に無くて本システムにあるもの

調査で確認した Peatix の構造的制約のうち、**理由が本システムに当てはまらないため
採用しなかった**もの。

| Peatix の制約 | 本システム | 採用しない理由 |
|---|---|---|
| 参加者リストにメールアドレスが含まれない | 開示し、CSVにも出力する | 第三者主催者を保護するためのマルチテナント固有の制約。自社のみなら不要。**ただし Peatix 側もフォーム機能でメールアドレスを取得すれば回避できるため、差別化としては弱い** |
| フォーム取得データがイベント終了30日後に自動削除される | 保持する | **データ蓄積が本システムの価値そのもの** |
| チケット名を申込後に変更できない | 変更可 | 金銭を扱わないため、購入済み商品としての同一性を保つ必要がない |
| API連携が存在しない（CSV手動出力のみ） | Repository 層で抽象化し、全メソッドを Promise で定義 | サーバ導入時に業務ロジックを変えず API 実装へ差し替えられる状態を保つ（4-2） |

**Peatix の上3つの制約を解消し、参加者データを蓄積して次回に活用できる状態を作ることが
本システムの価値である。** 画面を持たない `person` エンティティを当初から保持しているのは
このためで、後から追加すると全 `applications` の付け替えが必要になる（4-5）。

> **解消済み（2026-07-28）。** かつてここには「『データ蓄積が価値』と宣言しながら
> `persons` を参照する画面が無い」という矛盾があった。**参加者名簿 S-10（F-92）を
> 追加して解消した。** 名寄せ済みの参加者を横断で一覧し、同一人物の参加履歴・来場回数・
> 最終申込日を表示し、CSV出力できる。申込の永続化（C-2）も入ったので、シードだけでなく
> 実際の申込が蓄積される。

**この差は Peatix の30日削除と直接対比できる。** 本システムは参加履歴を期限なく保持し、
名簿画面から「この人は過去に何回参加し、何回来場したか」を即座に引ける。

## 4. 調査の出典

公式ヘルプの記事を読み、以下の構造的制約を確認している。

- API連携が存在しない（CSV手動出力のみ）
- フォーム取得データがイベント終了30日後に自動削除される
- 参加者リストにメールアドレスが含まれない
