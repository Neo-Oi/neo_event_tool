## 1. システムの概要

### 1-1. 何をするシステムか

社外向けイベント（取引先・同業他社・一般の方が参加）の、公開から当日受付までを1つのツールで行います。
研修課題で、学習の対象は IndexedDB です。

一連の流れは次のとおりです。

```
イベントを作る → 公開する → URLと投稿文で告知する → 申込を受ける
  → 当日受付する → 名簿をCSVで出す → 次回に活かす
```

### 1-2. 作りの前提

| 項目 | 内容 |
|---|---|
| 成果物 | `index.html` 1枚（約4,100行）。JS と CSS も中に書く |
| ビルド | しない。npm もバンドラも使わない |
| サーバ | 持たない |
| データ | ブラウザの IndexedDB に保存（DB名 `neo_event_tool`、バージョン5） |
| 外部接続 | CDN 2件だけ。しかも QR を使うときにしか取りに行かない |
| 起動 | `python3 -m http.server 8010` を実行し、`http://127.0.0.1:8010/` を開く |
| 画面幅 | PC幅のみ（F-81。ただし今後見直す予定 → 引き継ぎ書 8章） |

`file://` で直接開くのは不可です。IndexedDB が使えないブラウザがあるためです。

### 1-3. この作りではできないこと

サーバがないため、次のことは原理的にできません。ごまかさずに書いておきます。
理由の詳しい区分は `Peatix比較.md` にあります。

- **端末をまたいだデータ共有**（主催者と参加者は、同じブラウザの中で役割を切り替えて再現しています。これは実装ではなく、デモのための見立てです）
- メールの送信、決まった時刻に自動で動かすこと
- 公開URL、SEO、イベントごとの OGP
- 複数の端末で同時に受付すること
- 参加者が別の端末から自分の申込を確認すること

## 2. システムの構成

### 2-1. 全体の形

```
┌──────────────── ブラウザ ────────────────┐
│                                          │
│  画面（S-1〜S-10）                        │
│      ↓ 表示に必要な計算を頼む              │
│  Domain … 残席や時期などを計算する          │
│  AppSvc … 申込まわりの処理をまとめる         │
│      ↓ データの読み書きを頼む               │
│  Repository … データ操作の窓口              │
│      ↓                                   │
│  DB … IndexedDB を Promise で包む          │
│      ↓                                   │
│  IndexedDB（9つのストア）                  │
└──────────────────────────────────────────┘
        ↕ QRを使うときだけ
   CDN（qrcode / jsQR）
```

上の層が下の層を呼びます。逆向きには呼びません。

### 2-2. 各層の役割

| 層 | 役割 | 決まりごと |
|---|---|---|
| 画面 | 表示と操作の受付 | データは必ず Repository 経由で読み書きする |
| AppSvc | 申込・キャンセル・受付・修正 | 主催者側と参加者側が同じ処理を呼ぶ（F-25） |
| Domain | 保存しない値の計算 | 時期・残席・進捗はここで毎回計算する |
| Repository | データ操作の唯一の窓口 | あとでサーバに差し替えられるようにしておく |
| DB | IndexedDB の Promise 化とバージョン移行 | コールバックを上の層に見せない |

画面から `DB` を直接呼ぶのは違反です。`tests/guard.js` が自動で見つけます。

## 4. 画面の設計

### 4-1. 画面の一覧

| # | 画面 | 誰が見るか | 中身 |
|---|---|---|---|
| S-1 | ダッシュボード | 主催者 | 指標 → ヒートマップ → 要対応 → カレンダー |
| S-2 | イベント一覧 | 主催者 | 時期の絞り込みと、イベントカード（1列） |
| S-3 | イベント作成・編集 | 主催者 | 5ステップの入力 |
| S-4 | イベント詳細 | 主催者 | 上部に状況を固定表示＋9つのタブ |
| S-5 | 設定 | 主催者 | デモデータ投入、初期化、実装区分 |
| S-6 | 公開ページ | 参加者 | イベントの案内と申込ボタン |
| S-7 | 申込フォーム | 参加者 | 入力と確認（同じ画面で切り替え） |
| S-8 | 申込完了 | 参加者 | 完了メッセージと確認URL |
| S-9 | マイ申込 | 参加者 | 一覧と詳細（同じ画面で切り替え） |
| S-10 | 参加者名簿 | 主催者 | パスワードを入れてから一覧 |

### 4-2. 画面の行き来

```
主催者   S-1 ⇄ S-2 → S-3
              ↓
             S-4 ──[複製]→ 新しい下書きの S-4
              └─[参加者ビューで確認]→ S-6
         S-10（独立したタブ）    S-5

参加者   S-6 → S-7 → S-8 → S-9
```

URLを直接開いた場合は次のように動きます（F-97）。処理したあとURLは元に戻します。

| URL | 開く画面 |
|---|---|
| `?event=<id>` | S-6 公開ページ（限定公開はこの方法でのみ見られる） |
| `?ticket=<token>` | S-9 の申込詳細 |
| `?preview=<id>` | S-6（下書きでも表示する） |

### 4-3. ナビゲーション

- 主催者タブ（4つ・中央揃え）… ダッシュボード／イベント／参加者／設定
- 参加者タブ（2つ）… イベントを探す／マイ申込
- 役割の切替はヘッダーに置く（タブと同じ列にしない）

S-4 のタブは9つです。申込／運営スレッド／運営Q&A／運営タスク／マニュアル／ファイル／お知らせ／告知／概要・編集。
このうち運営スレッドからファイルまでは、参加者には見せません。

### 4-4. 主催者と参加者で見え方が違うもの

| 対象 | 主催者 | 参加者 |
|---|---|---|
| 下書き | 見える | 見えない（`?preview=` のときだけ例外） |
| 限定公開 | 一覧に出る | 一覧に出ない。URLを直接開いたときだけ |
| 定員・残席 | 実数 | 残席、または「満席」 |
| 他人の申込 | 全部見える | 見えない |
| オンラインの視聴URL | — | 申込んだ人のマイ申込にだけ出す |

## 5. データの設計

### 5-1. ストアの一覧

| ストア | キー | インデックス | 何を入れるか |
|---|---|---|---|
| `events` | `id` | `status`, `startAt` | イベント |
| `persons` | `id` | `emailKey`（重複不可） | 人（メールアドレスでまとめる） |
| `applications` | `id` | `eventId`, `personId`, `token`（重複不可）, `[eventId,status]` | 申込 |
| `savedTokens` | `token` | `savedAt` | この端末で申込んだ控え |
| `messages` | `id` | `eventId`, `[eventId,channel]` | スレッド・Q&A・お知らせ |
| `tasks` | `id` | `eventId` | 運営タスク |
| `readStates` | `key` | `eventId` | 最後に読んだ時刻 |
| `manuals` | `eventId` | — | マニュアルの本文 |
| `files` | `id` | `eventId` | 共有ファイル（実体を含む） |

`messages` は `channel` の値で3つの用途を兼ねています（`thread` / `qa` / `notice`）。

### 5-2. 主な項目

**events**
`id, title, description, targetAudience, startAt, endAt, venueName, venueAddress, contactInfo,
coverImage, capacity, applyStartAt, applyDeadline, eventFormat, onlineUrl, onlineNote,
questions, status, visibility, groupId, copiedFromId, createdAt, updatedAt`

**applications**
`id, eventId, personId, token, status, checkinAt, cancelledAt, appliedAt, answers, searchText`

**persons**
`id, emailKey, email, name, nameKana, contactConsent, consentAt, createdAt`

### 5-3. 決めごと

| 決めごと | 理由 |
|---|---|
| 時期（受付前・受付中など）は保存しない | 日付と現在時刻から毎回計算する。保存するとズレが起きる（F-05） |
| 未読かどうかも保存しない | 最後に読んだ時刻だけ保存し、投稿時刻と比べて数える（F-79c） |
| 定員はイベントが持つ | チケット枠をやめたため（F-61 を反転） |
| 同じ人が同じイベントに複数の申込を持てる | キャンセルしたあと申し込み直せるようにするため（F-42） |
| メールアドレスの正規化は前後の空白を削って小文字にするだけ | やりすぎると別人を同じ人にまとめてしまう |
| 所属（会社・学校）は人ではなく申込に持つ | 所属は時期によって変わるため（F-98c） |
| 長い本文は別のストアに分ける | イベント一覧が全件読むので、そこに重いものを置かない |

### 5-4. バージョンの移り変わり

`onupgradeneeded` で、既にあるストアはそのまま、無いものだけ作ります。

| バージョン | 変更点 |
|---|---|
| v1 | events / ticketTypes / persons / applications / savedTokens |
| v2 | ticketTypes を削除、messages と tasks を追加 |
| v3 | readStates を追加 |
| v4 | manuals を追加 |
| v5 | files を追加 |

## 6. 外部との接続

| 相手 | 何のために | いつ | つながらないとき |
|---|---|---|---|
| CDN（qrcode） | QRコードを作る | マイ申込で「QRを表示」を押したとき | 氏名検索での受付を案内する |
| CDN（jsQR） | QRコードを読む | 申込一覧で「QRで受付」を押したとき | 同上 |
| X | 投稿画面を開く | 告知タブのボタン | — |
| LINE | URLを共有する | 同上 | — |
| 地図サービス | 会場の場所を開く | 住所があるとき | — |
| カメラ | QRの読み取り | QR受付の開始時 | エラーを出して氏名検索へ誘導 |

**起動しただけでは外部に通信しません。** QR以外はオフラインでも動きます。

> **未対応の課題：CDN のスクリプトに改ざん検知（SRI）を付けていません。**
> QR受付は申込一覧の画面で動くため、そこには参加者の個人情報があります。
> 万一 CDN が改ざんされると、そのスクリプトから IndexedDB の中身も読めてしまいます。
> 対応は保留中です（引き継ぎ書 8章）。

## 7. 非機能の設計

| 項目 | 方針 |
|---|---|
| 性能 | 想定件数（イベント数十、申込数百）なら全件読み込みで足ります。件数が増えたら、イベント一覧とダッシュボードを `eventId` での絞り込みに変えます |
| 認可 | 申込の閲覧はランダムなトークンで行います。メールアドレスは鍵にしません |
| 個人情報 | 扱うのは社外の方の情報です。ブラウザ内に平文で入るため、実在の個人情報は入れません |
| 名簿の保護 | パスワードを求めますが、**これは秘密を守るためではなく、うっかり開くのを防ぐためです**。HTMLを読めばパスワードは分かります（F-101） |
| CSV | `=` `+` `-` `@` で始まる値の先頭に `'` を付けます。表計算ソフトが数式として実行してしまうのを防ぐためです（F-49b） |
| 画面表示の安全性 | 利用者が入力した文字は必ずエスケープします。マニュアルの Markdown も、先に全体をエスケープしてから組み立てます |
| エラー表示 | 4種類に分けます（入力エラー／完了／システムエラー／確認） |
| バックアップ | ありません。ブラウザのデータを消すと失われます。持ち出しは CSV のみです |

## 8. 運用

| やりたいこと | 操作 |
|---|---|
| 最初にデータを入れる | 設定 →「デモデータを投入」（イベント40件・参加者24名・申込220件） |

## 9. 品質の確認

| 手段 | 内容 |
|---|---|
| `tests/guard.js` | 決まりごとを守れているかの自動チェック（npm 不要） |
| `tests/smoke.js` | 108件の自動テスト。受け入れ確認14項目も含む |
| CI | GitHub Actions。push のたびに両方を実行する |

次のものは自動テストでは確認できません。ブラウザで手動確認が必要です。

- ファイルや画像（Blob）の保存と取り出し
- ドラッグ&ドロップ
- カメラ
- CDN の実際の取得
- 画面のレイアウト
