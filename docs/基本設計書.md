## 1. システム概要

### 1-1. 目的

社外向けイベント（取引先・同業他社・一般の方が申込む）の、公開・告知・申込受付・当日受付・
名簿蓄積を1つのツールで行う。**研修課題であり、技術学習の対象は IndexedDB。**

到達点（要件定義書 1-3）: イベントを作成して公開し、告知用URLと投稿文を発行し、申込を
受け付け、当日の受付を行い、名簿を出力する。この一連が実データで一周する。

### 1-2. 成果物と制約

| 項目 | 内容 |
|---|---|
| 成果物 | **単一の `index.html`（約4,100行）。** JS・CSS はインライン |
| ビルド | **なし。** npm・バンドラ・トランスパイラを使わない |
| サーバ | **持たない。** ローカルHTTPサーバ経由で開く（`python3 -m http.server 8010`） |
| データ | ブラウザの IndexedDB（DB名 `neo_event_tool`、v5） |
| 外部依存 | CDN 2件のみ。**遅延読み込み**（QRの生成・読取時のみ取得） |
| 対象画面幅 | PC幅のみ（F-81。ただし社外向け転換に伴い再検討中——引き継ぎ書 8章） |

### 1-3. この構成から原理的にできないこと

**隠さずに構造として示す**のが本プロジェクトの評価軸（引き継ぎ書 4-1）。詳細は
`Peatix比較.md` 1-2 / 1-4。

- 端末間のデータ共有（**主催者と参加者は同一ブラウザ内の役割切替で代用**。実装ではなくデモ演出）
- メールの実送信・定時実行（cron）
- 公開URL・SEO・イベント単位の OGP 出し分け
- 複数端末での同時受付／参加者が別端末で申込を確認すること

## 2. システム構成

### 2-1. 論理構成

```
┌─────────────────────────────── ブラウザ ───────────────────────────────┐
│                                                                        │
│  [13] アプリシェル（ヘッダー／タブ／役割切替／ルータ／URL復帰）             │
│    ├─ 主催者ビュー: S-1 ダッシュボード / S-2 イベント一覧 / S-3 作成編集    │
│    │                S-4 イベント詳細 / S-5 設定 / S-10 参加者名簿          │
│    └─ 参加者ビュー: S-6 公開ページ / S-7 申込 / S-8 完了 / S-9 マイ申込     │
│                              ↓ 画面は文字列を組み立てて innerHTML に入れる  │
│  [4] Domain（時期の都度算出・残席・タスク集計）                            │
│  [4b] AppSvc（申込・キャンセル・チェックイン・修正。主催者/参加者で共通）     │
│                              ↓ 全メソッドが Promise を返す                 │
│  [3] Repository 層 ← ここで IndexedDB を閉じ込める（差し替え点）           │
│                              ↓                                          │
│  [2] DB（生 IndexedDB API を Promise でラップ／onupgradeneeded）          │
│                              ↓                                          │
│  IndexedDB "neo_event_tool" v5（9ストア）                                │
└────────────────────────────────────────────────────────────────────────┘
        ↕ 遅延読み込みのみ
   CDN: qrcode（QR生成） / jsQR（QR読取）
```

### 2-2. レイヤの責務

| 層 | 責務 | 守ること |
|---|---|---|
| 画面（[7]〜[13]） | 描画とイベント配線 | データアクセスは必ず Repository 経由。`DB.*` を直接呼ばない |
| AppSvc（[4b]） | 申込まわりの業務処理 | 主催者側・参加者側が**同じ関数**を呼ぶ（F-25） |
| Domain（[4]） | 算出ロジック（保存しない値） | 時期・残席・進捗はここで都度算出する |
| Repository（[3]） | データアクセスの唯一の窓口 | **サーバ API へ差し替えられる状態を保つ**（引き継ぎ書 4-2） |
| DB（[2]） | IndexedDB の Promise 化・スキーマ移行 | イベントベース API を上位に露出させない |

`tests/guard.js` が Repository 迂回を機械的に検出する（CI で実行）。

### 2-3. 動作環境

| 項目 | 内容 |
|---|---|
| 起動 | `python3 -m http.server 8010` → `http://127.0.0.1:8010/` |
| `file://` | **不可**（IndexedDB が利用できないブラウザがあるため / 3-2） |
| ネットワーク | 通常は不要。QR機能を使うときのみ CDN 取得 |
| 想定規模 | 1イベントあたり参加者数百人（要件定義書 1-2） |

### 4-2. ナビゲーション

```
主催者タブ（4つ・中央揃え）: ダッシュボード ／ イベント ／ 参加者 ／ 設定
参加者タブ（2つ）          : イベントを探す ／ マイ申込
役割切替はヘッダー（タブと同列にしない）
```

**S-4 のサブタブ（9つ・主催者ビュー限定）**

```
申込 ／ 運営スレッド[未読バッジ] ／ 運営Q&A ／ 運営タスク ／ マニュアル
／ ファイル ／ お知らせ ／ 告知 ／ 概要・編集
```

初期タブは「申込」（F-75）。運営スレッド〜ファイルは参加者に出さない（4-3）。

### 4-3. 画面遷移

```
主催者   S-1 ⇄ S-2 → S-3（作成・編集）
              ↓
             S-4 ──[複製]→ S-4（新しい下書き）
              └─[参加者ビューで確認]→ S-6（?preview= 相当）
         S-10（横断・独立タブ）   S-5

参加者   S-6 → S-7（入力→確認）→ S-8 → S-9
                                       ↑ ?ticket= から直接復帰

URL復帰（F-97）  ?event=<id>    → S-6（限定公開はこの経路のみ）
                 ?ticket=<token> → S-9 詳細
                 ?preview=<id>   → S-6（下書きの確認 / F-07）
                 処理後は history.replaceState で URL を戻す
```

### 4-4. 役割による見え方の差

要件定義書 4-3 のとおり。実装上の要点のみ：

- 下書きは参加者ビューに出さない（`?preview=` のときだけ例外）
- 限定公開は参加者の一覧に出さず、URL 直接指定でのみ閲覧・申込
- **オンライン視聴URLは公開ページに出さず、申込者のマイ申込にのみ表示**（F-93）
- 他人の申込は参加者から見えない。自分の申込は確認トークン経由のみ

## 5. データ設計

### 5-1. ストア一覧（IndexedDB `neo_event_tool` v5）

| ストア | キー | インデックス | 用途 |
|---|---|---|---|
| `events` | `id` | `status`, `startAt` | イベント |
| `persons` | `id` | `emailKey`（unique） | 人（メールアドレスで名寄せ） |
| `applications` | `id` | `eventId`, `personId`, `token`（unique）, `[eventId,status]` | 申込 |
| `savedTokens` | `token` | `savedAt` | この端末が持つ自分の申込控え（F-56） |
| `messages` | `id` | `eventId`, `[eventId,channel]` | スレッド／Q&A／お知らせ（`channel` で兼用） |
| `tasks` | `id` | `eventId` | 運営タスク |
| `readStates` | `key`（`eventId:channel`） | `eventId` | 既読位置（未読件数の算出用 / F-79c） |
| `manuals` | `eventId` | — | イベントマニュアル（Markdown 本文） |
| `files` | `id` | `eventId` | 共有ファイル（Blob 実体を含む） |

### 5-2. 主な項目

**events** — `id, title, description, targetAudience, startAt, endAt, venueName, venueAddress,
contactInfo, coverImage(Blob), capacity, applyStartAt, applyDeadline, eventFormat,
onlineUrl, onlineNote, questions[], status, visibility, groupId, copiedFromId,
createdAt, updatedAt`

**applications** — `id, eventId, personId, token, status, checkinAt, cancelledAt,
appliedAt, answers, searchText`

**persons** — `id, emailKey, email, name, nameKana, contactConsent, consentAt, createdAt`

### 5-3. 設計上の原則

| 原則 | 内容 | 根拠 |
|---|---|---|
| **時期を保存しない** | 受付前／受付中／受付終了／開催済は、受付開始日・締切と現在時刻から都度算出 | F-05, 引き継ぎ書 4-3 |
| **未読を保存しない** | 最終閲覧時刻だけ保存し、未読件数は投稿時刻との比較で算出 | F-79c |
| **定員はイベントが持つ** | `events.capacity`。チケット枠は廃止 | F-61（反転済み） |
| **`[eventId, personId]` に unique を張らない** | キャンセル後の再申込を許すため | F-42 |
| **`emailKey` の正規化は trim と小文字化のみ** | 過度な正規化は別人の誤統合を招く | 引き継ぎ書 4-5 |
| **所属を `persons` に持たせない** | 所属は時期で変わるため、カスタム質問で取得 | F-98c |
| **本文が長いものは別ストア** | `manuals` / `files` を `events` から分離（一覧が全件読むため） | F-99, F-102 |

### 5-4. スキーマ移行

`onupgradeneeded` で **create-if-missing 方式**。既存データを保持したままストアを追加する。

| ver | 変更 |
|---|---|
| v1 | `events` / `ticketTypes` / `persons` / `applications` / `savedTokens` |
| v2 | `ticketTypes` を削除（チケット制廃止）、`messages` / `tasks` を追加 |
| v3 | `readStates` を追加 |
| v4 | `manuals` を追加 |
| v5 | `files` を追加 |

## 7. 非機能設計

| 項目 | 方針 |
|---|---|
| 性能 | 想定件数（イベント数十／申込数百）では全件読み込みで足りる。イベント一覧とダッシュボードは `messages`・`tasks` を全件読むため、件数が増えたら `eventId` インデックスでの絞り込みに切り替える |
| 認可 | 申込の閲覧は `crypto.getRandomValues()` で生成したトークン。**メールアドレスを鍵にしない**（引き継ぎ書 4-6） |
| 個人情報 | 扱うのはすべて社外の方＝第三者の個人情報。ブラウザ内に平文で保存されるため、**実在の個人情報を投入しない**。参加者名簿は閲覧前にパスワードを求めるが、**これは秘匿ではなく操作の抑止**（F-101） |
| CSV 安全性 | `=` `+` `-` `@` タブ CR で始まる値に `'` を付ける（**CSVインジェクション対策** / F-49b） |
| XSS | ユーザー由来の文字列は必ず `Util.esc` を通す。マニュアルの Markdown は**先に全体をエスケープしてから**組み立て、本文中の HTML を解釈しない（F-99d） |
| エラー | 4分類（入力エラー＝フィールド直下／完了＝トースト／システムエラー＝上部バナー／取り消せない操作＝確認モーダル）（F-84〜F-87） |
| 可用性・バックアップ | **なし。** ブラウザのデータを消せば失われる。エクスポートは CSV のみ |
