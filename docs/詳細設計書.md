## 0. この文書について

`基本設計書.md` が「どう実現するか」を外から見た形で書いたものなのに対して、
この文書は**中身をどう組んだか**を書いています。

コードを直す人が最初に読む想定です。特に **6章（壊れやすいところ）** と
**9章（変更時のチェックリスト）** は、直す前に目を通してください。

**直し方の原則**：ファイル全体を作り直さず、`// ===== [n] 名前 =====` で区切られた
区画の中だけを直します。区画の並び順は `tests/guard.js` が確認しています。

## 2. データの読み書き

### 2-1. `DB`（区画 [2]）

IndexedDB は結果を `onsuccess` / `onerror` というイベントで返します。
そのままだと使いにくいので、この区画で Promise に変換します。

```js
open()                              // DBを開く。必要ならバージョン移行する
put / get / getAll / remove         // 1件ずつの操作
getAllByIndex(store, index, value)  // インデックスで絞って取得
bulkPut(entries)                    // 複数ストアをまとめて1回の書き込みにする
reset()                             // DBを消して作り直す
```

**イベント形式の書き方は、この区画の外に出しません。**

### 2-2. `Repo`（区画 [3]）

| ストア | 使えるメソッド |
|---|---|
| `events` | all, get, put, remove |
| `persons` | all, get, byEmailKey, put |
| `applications` | all, get, byEvent, byPerson, byToken, put |
| `savedTokens` | all, get, put |
| `messages` | all, byEvent, put, remove |
| `tasks` | all, byEvent, put, remove |
| `readStates` | all, get, put |
| `manuals` | get, put, remove |
| `files` | byEvent, get, put, remove |
| 共通 | bulkPut, reset |

全部 Promise を返します。あとでサーバのAPIに差し替えるとき、
**ここだけ書き換えれば上の層は変えずに済む**ようにするためです。

> **必要なメソッドが無いときは、ここに足してください。`DB` を直接呼ばないこと。**
> 以前、`Repo` に `all()` が無かったせいでダッシュボードが `DB.getAll()` を
> 直接呼んでしまったことがあります。今は `tests/guard.js` が見つけます。

### 2-3. 書き込みの注意

IndexedDB のトランザクションは、**待っている間に他の非同期処理を挟むと勝手に閉じます。**
`fetch` や `FileReader` を途中で `await` すると失敗します。

そのため `bulkPut` は、**書き込むデータを全部そろえてから**トランザクションを始めます。
複数のデータをまとめて保存する場面（申込の確定、タスクの並べ替え、ファイルの複数追加）は
すべてこの形です。

```js
// ファイル追加の例。File は Blob なので、そのまま入れられる
const entries = picked.map(f => ({ store:"files", record:{ ..., blob:f } }));
await Repo.bulkPut(entries);
```

## 3. 計算のロジック（`Domain` / 区画 [4]）

### 3-1. 時期の判定 `timing(ev, now)`

保存せず、呼ばれるたびに計算します。上から順に見て、最初に当てはまったものを返します。

| 順 | 条件 | 結果 |
|---|---|---|
| 1 | 中止になっている | 中止 |
| 2 | 終了日時を過ぎた | 開催済 |
| 3 | 申込締切日の 23:59:59 を過ぎた | 受付終了 |
| 4 | 受付開始日の 00:00:00 より前 | 受付前 |
| 5 | どれでもない | 受付中 |

**順番に意味があります。** 中止を先に見ないと、中止したイベントが「開催済」になってしまいます。
受付開始日が未設定なら 4 は当てはまらず、公開と同時に受付中になります。

### 3-2. 定員と残席

```
有効な申込 = 状態が「申込済」または「チェックイン済」（キャンセルは除く）
残席 = 定員 − 有効な申込の数
定員間近 = 残り3席以下、または定員の10%以下
```

### 3-3. タスクの集計

```
状態は4つ … 未対応 / 処理中 / 処理済 / 完了
期限超過 … 期限日を過ぎていて、まだ「処理済」でも「完了」でもないもの
```

「処理済」を期限超過に数えないのは、**作業自体は終わって確認待ちの状態**だからです。
赤く出すと、本当に手を打つべきものが埋もれます。

## 4. 申込の処理（`AppSvc` / 区画 [4b]）

主催者側と参加者側が**同じ関数**を呼びます。画面から `Repo.applications.put` を
直接呼ばないでください。

### 4-1. `apply()` — 申込の確定

```
1. イベント・申込一覧・人 を同時に読む

2. 順に確認して、引っかかったらエラーを返す
   ・公開中でない            → このイベントには申込できません
   ・受付中でない            → 受付前／受付終了／開催済／中止 のため申込できません
   ・残席がない              → 定員に達したため申込できません
   ・同じ人の有効な申込がある → 既に申込済みです

3. 人のデータを用意する（メールアドレスが同じなら既存の人を使い、氏名は最新に更新）
4. 申込のデータを用意する（トークンを発行、検索用の文字列も作る）
5. この端末用の控えを用意する
6. 3〜5 をまとめて1回で書き込む
```

キャンセルしたあとの申し込み直しはできます。2 の最後の条件が「**有効な**申込」を
見ているためです。

### 4-2. その他の関数

| 関数 | すること |
|---|---|
| `cancel()` | 状態をキャンセルに変える。**レコードは消さない** |
| `setCheckin()` | チェックイン ⇄ 取消。記録するのは操作した時刻（来場時刻ではない） |
| `editApplicant()` | 人の情報を直し、その人の全申込の検索用文字列を作り直す。既に他の人が使っているメールアドレスには変えられない |
| `validate()` | 氏名50字、カナはひらがな・カタカナのみ50字、メールは形式と254字 |

## 5. 主な処理の流れ

### 5-1. イベントの保存（`Wizard` / 区画 [12b]）

```
「保存して次へ」を押す
  ↓
入力を集める
  ↓
ステップ1でイベント名が空なら止める
  ↓
一般公開から限定公開に戻そうとしていたら止める
  ↓
保存する（定員が既存の申込数を下回るときは止める）
  ↓
次のステップへ
```

押すたびに保存するので、途中でやめても入力した分は下書きとして残ります。

「公開する」を押したときは、先に公開前チェックを行い、不備があれば公開させません。
状態の変更は一方向です。公開後は下書きに戻せず、削除もできません。

### 5-2. URLから開いたとき（`App` / 区画 [13]）

```
起動
  ↓
DBを開く
  ↓
URLに ?event= / ?ticket= / ?preview= があるか見る
  ├ あった → その画面を出す。URLは元に戻す
  └ なかった → 通常の最初の画面を出す
```

URLを元に戻すのは、再読み込みしたときに同じ処理が走らないようにするためです。

### 5-3. 未読の数え方（`Ops` / 区画 [9b]）

```
保存するもの … そのイベント・その用途を「最後に見た時刻」だけ
未読の数     … その時刻より後に投稿されたものの件数
```

一度も開いていないイベントは、全部が未読になります。これは正しい動きです。

スレッドのタブを開いた時点で「見た時刻」を更新し、タブのバッジを消します。

### 5-4. Markdown の表示（`Util.markdown` / 区画 [1]）

外部のライブラリを使わず、自前で処理しています。
プレビューが標準の表示なので、CDN につながらないとマニュアルが読めない、
という状態を作りたくないためです。

```
1. 先に本文全体をエスケープする（入力されたHTMLをタグとして扱わないため）
2. 行ごとに種類を判定する（見出し・表・引用・箇条書き・コードなど）
3. 太字やリンクなどを置き換える
```

対応している記法：見出し、箇条書き（チェックボックス付きも可）、番号付き、引用、
水平線、コード、表、太字、取り消し線、リンク。

### 5-5. ヒートマップの色分け（`Dashboard` / 区画 [7]）

```
数えるもの … 全イベントの申込。ただし中止イベントの分は除く
除かないもの … 申込のキャンセル（「申し込んだ」という事実を見たいため）
期間 … 今週の月曜から26週さかのぼる（ちょうど 7×26＝182マス）
色 … 5段階（0件／1件／少ない／普通／多い）
```

「少ない・普通・多い」の境目は、**最大値ではなく分布**で決めています。
1日だけ極端に多い日があると、最大値を基準にした場合に他の日が全部薄くなってしまうためです。

## 6. 壊れやすいところ

**直す前にここを読んでください。** どれも実際に一度壊した箇所です。

### 6-1. ドラッグ中に画面を作り直さない（`Tasks` のボード）

掴んでいる要素の親を作り直すと、その要素が宙に浮いて、以降の操作が画面に反映されなくなります。
ドラッグ中は掴んでいる要素そのものを動かし、保存と再描画はドロップした後にまとめて行います。

### 6-2. 入力中に textarea を作り直さない（`Manual` の分割表示）

作り直すとカーソルの位置が先頭に飛びます。プレビュー側だけを差し替えてください。

### 6-3. Markdown の引用記号

本文を先にエスケープしているので、行頭の `>` は `&gt;` に変わっています。
引用を判定する正規表現は `&gt;` で書く必要があります。

### 6-4. 検索語はイベントをまたいだら消す（`EventDetail`）

検索語を変数で持っているため、別のイベントを開いたときに明示的に消しています。
消さないと、前のイベントの検索語が残って「申込が0件」に見えます。

### 6-5. ファイルは読み直さない（`Files`, カバー画像）

`File` はそのまま保存できます。`FileReader` を通すと非同期処理が挟まり、
トランザクションが閉じる問題に近づきます。

ファイル名・サイズ・種類は、実体とは**別の項目にも持たせています**。
一覧表示が実体の取り出しに依存しないようにするためです。

## 7. エラーの扱い

| 種類 | 出し方 |
|---|---|
| 入力エラー | 該当する項目のすぐ下に出し、最初のエラーへカーソルを移す |
| 完了 | 右下にトースト。数秒で消える |
| システムエラー | 画面上部にバナー。閉じるまで残る |
| 取り消せない操作 | 確認モーダル |

`AppSvc` はエラーを投げるだけで、画面表示はしません。
呼び出した画面側がバナーやトーストに出します。

## 8. テストと CI

| ファイル | 内容 |
|---|---|
| `tests/guard.js` | 決まりごとを守れているかの確認。npm 不要で動く |
| `tests/smoke.js` | 108件の自動テスト |
| `.github/workflows/test.yml` | push のたびに両方を実行する |

`guard.js` は、コメントや文字列を取り除いてから判定しています。
単純に文字列を探すだけだと、コメントに書いた「`Math.random()` は使わない」に
反応してしまうためです。

自動テストで確認できないもの（ファイル保存、ドラッグ&ドロップ、カメラ、CDN、見た目）は
`tests/README.md` にまとめてあります。

## 9. 変更するときのチェックリスト

1. 区画の中だけを直したか（ファイル全体を作り直していないか）
2. データの読み書きは `Repo` を通したか
3. 利用者が入力した文字をエスケープしたか
4. トランザクションの中で他の待ち処理を挟んでいないか
5. 新しいストアが必要なら、DBのバージョンを上げたか
6. 仕様が変わるなら `要件定義書.md` に書いたか
7. `node tests/guard.js` と `node tests/smoke.js` が通るか
