## 2. データアクセス層

### 2-1. `DB`（[2]）

```js
open()                          // indexedDB.open → onupgradeneeded で移行 → Promise<IDBDatabase>
put(store, rec) / get(store, key) / getAll(store) / remove(store, key)
getAllByIndex(store, index, value)
bulkPut(entries)                // entries: [{store, record}, ...] を1トランザクションで
reset()                         // deleteDatabase → open（F-32）
```

`_wrap(req)` が `onsuccess`/`onerror` を Promise に変換する。**この関数の外に
コールバックを漏らさない**（技術方針）。単一レコード操作は各呼び出しが独立した
トランザクションになる。

### 2-2. `Repo`（[3]）

| ストア | メソッド |
|---|---|
| `events` | `all, get, put, remove` |
| `persons` | `all, get, byEmailKey, put` |
| `applications` | `all, get, byEvent, byPerson, byToken, put` |
| `savedTokens` | `all, get, put` |
| `messages` | `all, byEvent, put, remove` |
| `tasks` | `all, byEvent, put, remove` |
| `readStates` | `all, get, put` |
| `manuals` | `get, put, remove` |
| `files` | `byEvent, get, put, remove` |
| 横断 | `bulkPut(entries)`, `reset()` |

**全メソッドが Promise を返す。** サーバ API へ差し替える際、ここだけを書き換えれば
上位のロジックが変わらない状態を保つ（引き継ぎ書 4-2）。

> **必要なメソッドが無いときは Repo に足す。`DB.*` を直接呼ばない。**
> 過去に一度、`Repo` に `all()` が無かったためダッシュボードが `DB.getAll("messages")` を
> 直接呼ぶ違反が入った。現在は `tests/guard.js` が検出する。

### 2-3. トランザクションの制約

**IndexedDB のトランザクションはマイクロタスクキューが空になると自動的に閉じる。**
トランザクション内で `fetch` / `setTimeout` / `FileReader` を `await` すると失敗する。

対策として `bulkPut` は**レコードを全部組み立ててから**トランザクションを開始する。
複数ストアにまたがる更新（申込確定、タスクの並べ替え、ファイルの複数追加）はすべてこの形。

```js
// ファイル追加の例。File は Blob なので FileReader を通さない（通すと非同期が挟まる）
const entries = picked.map(f => ({ store:"files", record:{ ..., blob:f } }));
await Repo.bulkPut(entries);
```

## 3. ドメインロジック（`Domain` / [4]）

### 3-1. 時期の算出 `timing(ev, now)`

**保存せず毎回算出する**（F-05）。判定は上から順に評価し、最初に一致したものを返す。

| 順 | 条件 | 戻り値 |
|---|---|---|
| 1 | `status === "cancelled"` | `{phase:"cancelled", label:"中止"}` |
| 2 | `endAt < now` | `{phase:"held", label:"開催済"}` |
| 3 | 締切当日の 23:59:59 を過ぎた | `{phase:"closed", label:"受付終了"}` |
| 4 | 受付開始日の 00:00:00 前 | `{phase:"before", label:"受付前"}` |
| 5 | 上記以外 | `{phase:"open", label:"受付中"}` |

**順序に意味がある。** 中止を最優先にしないと、中止イベントが「開催済」になる。
`applyStartAt` 未設定なら 4 は成立せず、公開と同時に受付中になる（F-45b）。

### 3-2. 定員と残席

```js
isValidApp(a)  // status が "applied" または "checkedin"（キャンセルを除き、チェックイン済を含む）
usedSeats(apps) = apps.filter(isValidApp).length
remaining(ev, apps) = (ev.capacity || 0) - usedSeats(apps)
nearlyFull(ev, apps)  // 残席3以下 または 定員の10%以下（F-58）
```

### 3-3. タスク集計

```js
TASK_FLOW = ["todo", "doing", "review", "done"]
taskOverdue(t, now)   // dueDate の 23:59:59 を過ぎ、かつ status が done でも review でもない
taskSummary(tasks)    // { by:{todo,doing,review,done}, total, done, rate, overdue }
```

**期限超過から「処理済（review）」を除外している。** 作業は終わって確認待ちの状態なので、
赤く出すとノイズになる。この判定は `Domain.isValidApp` とは目的が違うので揃えない。

## 4. 申込の業務処理（`AppSvc` / [4b]）

F-25 が「主催者と参加者で処理は共通」と定めるため、**両方がここを呼ぶ。**
画面から `Repo.applications.put` を直接呼ばない。

### 4-1. `apply(eventId, input)` — 申込の確定

```
input = { name, kana, email, consent, answers }

1. events / applications / persons を並列取得
2. 検証（この順で最初の失敗で throw）
   ├ イベントが published でない        → 「このイベントには申込できません」
   ├ timing().phase !== "open"          → 「{受付前|受付終了|開催済|中止}のため申込できません」
   ├ remaining <= 0                     → 「定員に達したため申込できません」
   └ 同一人物の有効な申込が既にある     → 「このイベントには既に申込済みです」（F-17）
3. person を組み立て（emailKey で名寄せ。既存があれば氏名・カナを最新に更新）
4. application を組み立て（token = crypto 16バイト、searchText を正規化して保持）
5. savedTokens に控えを作る（F-56）
6. bulkPut で persons / applications / savedTokens を1トランザクション投入
```

**定員判定は直前の読み取りに基づく。** 単一ブラウザ前提のため競合は考慮しない。
キャンセル後の再申込は許す（F-42。有効な申込が無ければ 2-4 を通過する）。

### 4-2. その他

| 関数 | 内容 |
|---|---|
| `cancel(appId)` | `status = "cancelled"`, `cancelledAt` を記録。**レコードは消さない** |
| `setCheckin(appId, on)` | `checkedin` ⇄ `applied`。`checkinAt` は**操作時刻**（来場時刻ではない / F-24）。キャンセル済みは拒否 |
| `editApplicant(appId, {name,kana,email})` | `person` を更新し、**同一人物の全申込の `searchText` を再計算**。既に別人が使っている `emailKey` への変更は拒否（誤統合の分離が困難なため / 4-5） |
| `validate(d)` | 氏名50字・カナ（ひらがな/カタカナのみ）50字・メール254字。申込フォームと主催者の修正欄で共用 |

## 5. 主要処理フロー

### 5-1. イベントの作成・保存（`Wizard` / [12b]）

```
render(el, eventId)
  └ form を初期化（新規 or 既存から復元）、questions を配列で保持

「保存して次へ」
  ├ collect()        現在ステップの入力を form へ（collectQuestions も同時に）
  ├ ステップ1でタイトル未入力なら中断（F-70）
  ├ guardVisibility() 一般公開→限定公開への後退を拒否（F-66）
  └ persist(status)
       ├ buildRecord()  トランザクション前にレコードを完成させる
       ├ F-41 検査      定員 < 有効な申込数 なら中断
       └ Repo.events.put()

「公開する」
  └ publishIssues() が空でなければ公開させない（F-06）。空なら確認モーダル → persist("published")
```

**状態遷移は一方向**（F-37）。公開済み・中止済みでは footer が「変更を保存」だけになり、
公開・削除ボタンを出さない。

### 5-2. URL からの復帰（`App.routeFromUrl` / [13]）

```
起動（[14]）
  └ DB.open() → routeFromUrl() が true を返せばそこで描画、false なら通常の初期画面

routeFromUrl()
  ├ ?ticket= → 申込を検索 → 未保存なら savedTokens に控えを作る → S-9 詳細へ
  ├ ?event=  → S-6（限定公開はこの経路でのみ閲覧可能）
  ├ ?preview= → previewId を立てて S-6（下書きでも表示 / F-07）
  └ いずれも history.replaceState で URL を戻す（再読込で再発火させない）
```

### 5-3. 未読の算出（`Ops` / [9b]）

```
readStates: { key: `${eventId}:${channel}`, eventId, channel, lastReadAt }

unreadOf(msgs, channel, reads, eventId)
  = その channel の投稿のうち createdAt > lastReadAt の件数
    （readState が無ければ全件が未読 ＝ 一度も開いていない）

renderThread() の冒頭で markRead() を呼び、onRead コールバックで
EventDetail のサブタブのバッジを消す（ペイン全体は再描画しない）
```

**「未読かどうか」は保存しない。** 時期を保存しないのと同じ理由（4-3）。

### 5-4. Markdown 描画（`Util.markdown` / [1]）

**外部ライブラリを使わない。** プレビューが既定ビューなので、CDN 不達でマニュアルが
読めなくなる状態を作らない。

```
1. esc() で全体をHTMLエスケープ  ← 本文中のHTMLはタグとして解釈されない（F-99d）
2. 行単位でブロックを判定
   フェンスコード / 見出し / 水平線 / 表 / 引用 / 箇条書き / 番号付き / 段落
3. インライン: `code` ** ** ~~ ~~ * * [text](http(s)://…)
```

> **罠**: 1 のエスケープにより、行頭の `>`（引用）は `&gt;` になっている。
> ブロック判定の正規表現は `&gt;` で書く必要がある。**実際にここで一度バグらせた。**
> リンクは `https?:` のみ許可（`javascript:` を通さない）。

### 5-5. ヒートマップの階調（`Dashboard.heatmapHtml` / [7]）

```
集計   中止イベントの申込を除外（F-40）／申込側のキャンセルは除外しない
       ＝「申込という行動があった事実」を見るため。Domain.isValidApp と揃えない
期間   今週の月曜（F-60）から遡って26週 → ちょうど 7×26 = 182 セル
階調   0件 / 1件 / p33未満 / p66未満 / それ以上
       パーセンタイルの母集団は「2件以上の日」
```

**母集団を限定する理由**: 0件を含めると期間の大半が0のとき `p33=p66=0`、1件を含めると
1件の日が大半のとき `p33=p66=1` になり、どちらも中間の段が空になる（実データで両方発生）。

## 6. 画面実装の共通ルール

| ルール | 内容 |
|---|---|
| 描画 | `el.innerHTML = テンプレート文字列` の全置換。仮想DOMは持たない |
| エスケープ | **ユーザー由来の文字列は必ず `Util.esc()` を通す** |
| 日付 | `Util.fmtRange(startAt, endAt)`（開催日時）／`Util.fmtDate`（日付のみ）。個別に整形を書かない |
| イベント配線 | `innerHTML` 差し替えの**直後**に `onclick` などを張り直す |
| 状態 | 画面固有の状態はモジュールスコープの変数（`tab`, `query`, `expandedId`, `viewMonth` など） |

### 6-1. 再描画で壊れやすい箇所

> **ドラッグ中に `innerHTML` を全置換しない**（`Tasks` のボード）。
> 掴んだ要素が親を失い、以後の操作が画面に反映されなくなる。`dragover` では
> 掴んでいる要素そのものを `insertBefore` で動かし、保存と再描画は `drop` 後にまとめて行う。

> **入力中に textarea を作り直さない**（`Manual` の分割ビュー）。
> カーソル位置が飛ぶ。プレビュー側の `innerHTML` だけを差し替える。

> **絞り込み語はイベントを跨いだら解除する**（`EventDetail`）。
> モジュール変数で保持しているため、`render()` で明示的にクリアしている。

### 6-2. Blob の扱い

| 用途 | 実装 |
|---|---|
| カバー画像 | `events.coverImage` に File をそのまま保存。表示時に `URL.createObjectURL`。URL は上限20件で古いものから `revokeObjectURL` |
| 共有ファイル | `files.blob` に File をそのまま保存。`size`/`type`/`name` は**別フィールドにも持つ**ので、一覧表示が Blob の取り出しに依存しない |

> **`FileReader` を通さない。** File は Blob なので読み直す必要がなく、通すと非同期処理が
> 挟まってトランザクションの罠に近づく。

## 7. エラー処理

| 種類 | 表示 | 実装 |
|---|---|---|
| 入力エラー | 該当フィールド直下＋最初のエラーへフォーカス（F-84） | 各画面の `showErr` / `err` クラス |
| 完了 | 右下トースト・数秒で自動消滅（F-85） | `FB.toast(msg)` |
| システムエラー | 上部バナー・閉じるまで残る（F-86） | `FB.error(msg)` |
| 取り消せない操作 | 確認モーダル（F-87） | `FB.confirmModal({title, body, okLabel, danger, onOk})` |

`AppSvc` は業務エラーを `throw new Error(メッセージ)` で返し、**呼び出し側の画面が
`FB.error` で表示する。** サービス層は DOM に触れない。

## 9. 変更時のチェックリスト

1. 区画マーカーの中で編集したか（全体を再生成していないか）
2. データアクセスは `Repo` 経由か
3. ユーザー由来の文字列に `Util.esc` を通したか
4. トランザクション内で IndexedDB 以外を `await` していないか
5. 新しいストア／インデックスが要るならスキーマのバージョンを上げたか
6. 要件が変わるなら**要件定義書本文**に反映したか（CLAUDE.md のログは1行要約のみ）
7. `node tests/guard.js` と `node tests/smoke.js` が通るか
