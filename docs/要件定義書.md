## 1. 概要

### 1-1. 成果物

**単一HTMLファイルの機能プロトタイプ。** サーバを持たず、ブラウザ内（IndexedDB）にデータを永続化する。

データが永続化され、状態が遷移し、検索が動作する。見た目のみのモックアップではない。

### 1-2. 前提

| 項目 | 内容 |
|---|---|
| 主催者 | 自社のみ（マルチテナントではない） |
| ネットワーク | **インターネットが使える前提とする。** オフライン環境は考慮しない（3-2） |
| 対象範囲 | **社外向けイベントのみ**（2026-07-28 改訂。旧: 社内向け）。取引先・同業他社・一般の方が申込む。対象範囲を選ばせる項目は持たない（F-98） |
| 想定規模 | 1イベントあたり参加者数百人 |
| 参加者 | 不特定多数の社外の方（取引先・同業他社・一般）。**イベントを探す・申込むのにログインは要らない。マイ申込の一覧だけログインが必要**（F-107。2026-07-29 改訂） |
| 金銭 | 対象領域外 |
| データ | ダミーのみ。実在の個人情報は投入しない |

### 1-3. 到達点

> 1つのイベントを作成して公開し、告知用URLと投稿文を発行し、申込を受け付け、当日の受付を行い、名簿を出力できる。この一連の流れが実データで一周する。

## 2. 機能要件

### 2-1. イベントの公開

| # | 要件 |
|---|---|
| F-01 | イベントを作成・編集できる。削除は下書き状態のみ可能とする |
| F-02 | 入力項目：タイトル／説明／対象者／開始・終了日時／会場名・住所／定員／申込締切 |
| F-03 | カバー画像を設定できる（任意項目。未設定時はプレースホルダーを表示） |
| F-03b | **参加者側の一覧にもカバー画像を帯で表示する**（2026-07-29 追加）。「イベントを探す」（S-6の一覧）と「マイ申込」（S-9の一覧）のカードの上部に出す。文字だけの一覧は寂しく、どのイベントかを見分ける手掛かりにもなるため。高さは固定し（一覧132px／マイ申込96px、640px以下ではそれぞれ108px／84px）、未設定・取り出せない場合も同じ高さの下地を出して並びを崩さない。**シードのカバー画像は SVG を実行時に組み立てて Blob として保存する**——画像ファイルの同梱は単一HTMLを肥大させるため行わず、データURIも使わない。色はイベントIDから決定的に決め（`Math.random()` は使わない）、開催形式（現地／オンライン／ハイブリッド）で図柄を変える。**SVG に文字は入れない**（`img` で描くため書体が環境依存になり、日本語が表示できない環境がある）。下書きはカバー未設定のまま残し、プレースホルダー表示も確認できるようにする |
| F-04 | 状態を下書き・公開・中止に変更できる。遷移は一方向（2-6参照） |
| F-05 | 受付前・受付中・受付終了・開催済は、締切日時と現在時刻から都度算出する（保存しない） |
| F-06 | 公開前に不備を検出する（必須項目の未入力／締切が開催日より後／終了＜開始／開催日が過去） |
| F-07 | 下書き状態でも参加者ビューでの見え方を確認できる |
| F-08 | 申込ボタンの文言が状態により変わる（受付前／申込む／満席／受付終了／中止／終了）。「受付前」は `applyStartAt`（受付開始日）が未来の場合に出す |
| F-09 | ~~申込枠を持つ~~ **廃止**（2026-07-27）。チケット制の廃止に伴い申込は「申込」に一本化。定員は `events.capacity` が保持する |

### 2-2. 告知

| # | 要件 |
|---|---|
| F-10 | イベントごとの共有URLを発行し、コピーできる |
| F-11 | 投稿文を自動生成する（イベント名・日時・会場・URLを差し込む） |
| F-12 | 生成した投稿文を編集できる |
| F-13 | 投稿文をクリップボードにコピーできる |
| F-14 | X共有ボタンから、文・URL・ハッシュタグを含む投稿画面を開ける |
| F-15 | LINE共有ボタンからURLを共有できる（テキストは付加しない） |

### 2-3. 申込受付

| # | 要件 |
|---|---|
| F-16 | 参加者は氏名・カナ・メールアドレスで申込できる。3項目すべて必須とする。加えて主催者が定義したカスタム質問に回答する（F-91） |
| F-17 | 1人1枠1件とする（複数枚・代理申込は不可） |
| F-18 | 定員に達した場合は申込できない（キャンセル待ちは持たない）。定員判定はイベント単位で、有効な申込のみで行う（キャンセル済みを除き、チェックイン済みを含む） |
| F-19 | 申込完了時に、ランダムトークンを含む確認URLを発行し表示する |
| F-20 | 参加者は確認URLから申込内容を閲覧できる |
| F-21 | 申込フォームに、今後の案内受け取りに関する同意チェックボックスを設ける |

### 2-4. 参加者管理

| # | 要件 |
|---|---|
| F-22 | 申込一覧を表示できる |
| F-23 | 氏名・カナ・メールアドレスの部分一致で申込を絞り込める（入力に応じて即時反映） |
| F-24 | チェックインおよびその取り消しができる。開催済イベントでも制限しない。`checkinAt` には操作時刻を記録する（来場時刻ではない）。受付方法は氏名検索とQR読み取りの2通り（F-95） |
| F-25 | 主催者が申込をキャンセルできる。参加者もマイチケットから自分の申込をキャンセルできる。処理は共通とする |
| F-26 | 主催者が申込内容（氏名・メールアドレス）を修正できる |
| F-27 | 残席を一覧・詳細・公開ページに表示する |
| F-28 | 参加者リストをCSV形式で出力できる。カスタム質問の回答も列として出力する（F-91） |

### 2-5. 横断

| # | 要件 |
|---|---|
| F-29 | 主催者ビューと参加者ビューを切り替えられる |
| F-30 | ダッシュボードに指標を表示する（進行中のイベント数／今週の申込数／要対応件数／下書き件数） |
| F-31 | 要対応リストを表示する（今日・明日開催／満席・定員間近／下書きのまま放置） |
| F-31b | 要対応の各項目には、条件だけでなく**次に何をするか**を書く。あわせて開催日時・申込数・残席と、そのイベントに残っている作業（期限超過タスク／未対応タスク／未解決Q&A）を添える。緊急度（本日開催・満席＞明日開催・定員間近＞下書き放置）の順に並べる |
| F-32 | データベースを初期化できる |
| F-33 | デモ用のシードデータを投入できる |
| F-33b | シードには**過去アーカイブを中心に約2年ぶん**を含める。イベント40件（うち過去31件）、参加者24名、申込220件程度。「フォーム取得データを期限なく保持する」という本システムの価値（2章）は、**蓄積された状態でないと確認できない**ため。同一人物が複数回参加している状態を作り、参加者名簿（F-92）の履歴表示が意味を持つようにする。生成に `Math.random()` は使わず、添字から決定的に組み立てる（再現性のため / 禁止事項） |
| F-34 | データベースの操作失敗を画面に表示する |
| F-35 | データが存在しない場合に案内を表示する |
| F-36 | ~~実装済・疑似実装・対象外の区分を一覧で表示する~~ **廃止**（2026-07-30 指示）。設計・進捗の情報であり利用者が使う機能ではないため、画面から外した。実装状況の記録は `機能一覧.md` と  で保持する |

### 2-6. 状態遷移

| # | 要件 |
|---|---|
| F-37 | イベントの状態遷移は一方向とする。`下書き → 公開 → 中止`。逆方向の遷移はできない |
| F-38 | 公開ボタンと中止ボタンには確認ダイアログを表示する。いずれも取り消せない操作であるため |
| F-39 | 中止時に既存の申込は変更しない。参加者には「中止されました」を表示する |
| F-40 | 中止したイベントの申込は、ダッシュボードの申込集計から除外する |
| F-41 | イベントの定員は、そのイベントの有効な申込数を下限とする。それより少ない値には変更できない |
| F-42 | キャンセル後の同一イベントへの再申込を許す。`applications` の `[eventId, personId]` に一意制約を設けない |
| F-43 | キャンセル済みの申込の確認URLを開いた場合、「キャンセルされました」を表示する |
| F-44 | イベント一覧は時期のトグルで絞り込む（未定／これから／終了・中止）。複数選択でき、初期表示は未定と これから をON、終了・中止をOFFとする |

### 2-7. 境界条件

| # | 要件 |
|---|---|
| F-45 | 申込締切は日付のみを設定する。締切当日の23:59:59まで受け付ける |
| F-45b | 受付開始も日付のみを設定する（任意）。開始当日の00:00:00から受け付ける。未設定の場合は公開と同時に受付を開始し、「受付前」は発生しない |
| F-46 | 日時の判定はすべて端末のローカル時刻で行う。タイムゾーンの変換は行わない |
| F-46b | 開催日時は開始と終了の両方を表示する。同じ日に終わる場合、終了は時刻のみを表示する（例: `2026/08/11 18:30 〜 20:30`）。主催者側・参加者側で同じ表記を使う |
| F-47 | 申込者検索は表記の違いを吸収する。`NFKC` 正規化（全角英数と半角カナを統一）、小文字化、カタカナからひらがなへの変換、空白の除去を行い、検索語と対象の双方に同じ正規化を適用する |
| F-48 | CSVはBOM付きUTF-8、改行コードCRLFで出力する |
| F-49 | CSVの値にカンマ・引用符・改行が含まれる場合は、値をダブルクォートで囲み、内部の引用符を2つに重ねてエスケープする |
| F-49b | **CSVインジェクション対策。** `=` `+` `-` `@` タブ CR で始まる値は先頭に `'` を付けて数式として解釈されないようにする。表計算ソフトはこれらを数式として実行するため、参加者が氏名欄に入れた値が名簿を開いた運営側で動作しうる |
| F-50 | 下書き保存はタイトルのみ必須とする。公開時にタイトル・説明・開催日時・会場名・定員・申込締切を必須とし、F-06で検出する。対象者・住所・カバー画像は任意 |
| F-51 | 開催日時が未設定の下書きは、イベント一覧の先頭にまとめて表示する |
| F-52 | カナ欄はひらがなとカタカナの両方を受け付け、保存時にカタカナへ変換する。許容文字はひらがな・カタカナ・長音記号・空白のみとし、それ以外は入力エラーとする |
| F-53 | メールアドレスの検証は緩く行う。`@` を1つ含み、その前後に文字があり、ドメイン部にドットが1つ以上あることのみを確認する |
| F-54 | 文字数上限：タイトル100文字、説明2000文字、対象者200文字、会場名100文字、住所200文字、氏名50文字、カナ50文字、メールアドレス254文字 |
| F-55 | 定員は1以上9999以下の整数とする |
| F-56 | 申込完了時に、確認用トークンを参加者ビュー側に保存する。参加者ビューを再訪した際、保存済みトークンからマイチケットへ遷移できる |
| F-57 | **改訂**（2026-07-29 / F-107）。マイ申込は、ログイン中の本人の申込一覧（`personId` で取得）と、選択した申込の詳細を表示する。画面はS-9内で切り替える。旧「保存済みトークン（`savedTokens`）の一覧」は、同じブラウザを使った別人の申込も並ぶため置き換えた |
| F-58 | 「定員間近」は、イベント全体の残席が3以下または定員合計の10%以下の場合とする |
| F-59 | 「下書き放置」は、下書き状態で7日以上更新がない場合とする |
| F-60 | 「今週」は月曜を起点とする |
| F-61 | **反転**（2026-07-27）。定員は `events.capacity` が保持する。イベント全体で1つの定員とし、残席はそこから算出する |
| F-62 | ~~有効な申込がある申込枠は削除できない~~ **廃止**（申込枠が無くなったため）。参照されているレコードを消さない原則は F-01 の「公開後は削除不可」に引き継ぐ |
| F-63 | ~~申込枠の名称は変更できる~~ **廃止**（申込枠が無くなったため） |
| F-64 | イベントに問い合わせ先欄（自由記述・任意・200文字以内）を持ち、公開ページに表示する。参加者から主催者へ連絡する唯一の手段となる |
| F-65 | 公開範囲を一般公開と限定公開から選べる。限定公開は参加者ビューの一覧に表示せず、イベントURLを直接開いた場合のみ閲覧と申込ができる |

**F-47の実装方針**：`applications` に正規化済みの検索用文字列（氏名・カナ・メールアドレスを連結して正規化したもの）を保持し、検索時は正規化した入力語と1回の部分一致で比較する。入力ごとに全件を正規化し直す実装は避ける。

既知の限界として、長音記号（ー）とハイフンの混同は吸収しない。

## 3. 非機能要件

### 3-1. 実装方式

| 項目 | 要件 |
|---|---|
| 形態 | HTMLファイル1枚。JS・CSSはインライン。CDN参照は可 |
| UI実装 | 素のJavaScript（フレームワークを使用しない） |
| データ保存 | IndexedDB |
| データアクセス | Repository層で抽象化し、全メソッドを非同期（Promise）で定義する |
| コード構成 | `// ===== [n] セクション名 =====` のマーカーで区画分割する |

### 3-2. 動作環境

| 項目 | 要件 |
|---|---|
| 起動方法 | ローカルHTTPサーバ経由（例：`python -m http.server`） |
| `file://` 直接開き | 不可（IndexedDBが利用できないブラウザが存在するため） |
| ネットワーク | **インターネットは利用できるものとする**（2026-07-28 決定）。オフライン環境での動作は要件に含めない |

### 3-3. データ設計

| ストア | 主な属性 |
|---|---|
| `events` | id, title, description, targetAudience, startAt, endAt, venueName, venueAddress, contactInfo, coverImage(Blob/任意), capacity, applyStartAt(date/任意), applyDeadline(date), eventFormat, onlineUrl, onlineNote, questions[], status, visibility, groupId, copiedFromId, createdAt, updatedAt |
| `persons` | id, emailKey, email, name, nameKana, contactConsent, consentAt, createdAt |
| `applications` | id, eventId, personId, token, status, checkinAt, cancelledAt, appliedAt, answers, searchText |
| `messages` | id, eventId, channel(`thread`/`qa`/`notice`), author, body, createdAt ほか channel 別の項目 |
| `tasks` | id, eventId, title, detail, assignee, status, priority, startDate, dueDate, order, createdAt, updatedAt, doneAt |
| `readStates` | key(`eventId:channel`), eventId, channel, lastReadAt（未読件数の算出用 / F-79c）。**通知（F-108d）は同じストアを使い、キーを `__notify:organizer` / `__notify:participant:<personId>` とする**（イベント横断のため） |
| `manuals` | eventId（主キー）, body（Markdown）, updatedAt（F-99）。本文が長くなるため `events` とは分ける |
| `files` | id, eventId, name, type, size, blob(Blob), uploadedAt, uploadedBy（F-102） |
| `savedTokens` | token, eventId, savedAt（参加者ビューが保持する自分の申込。F-56） |

| ストア | インデックス |
|---|---|
| `events` | `status` / `startAt` |
| `persons` | `emailKey`（unique） |
| `applications` | `eventId` / `personId` / `token`（unique） / `[eventId, status]`（複合） |
| `savedTokens` | `savedAt` |
| `messages` | `eventId` / `[eventId, channel]`（複合） |
| `tasks` | `eventId` |
| `files` | `eventId` |
| `readStates` | `eventId` |

補足：`persons` は申込時にメールアドレス（trim＋小文字化した `emailKey`）で名寄せして紐付ける。画面は持たないが、後から追加すると全 `applications` の付け替えが必要になるため、当初から保持する。`emailKey` の正規化はtrimと小文字化のみとし、それ以上は行わない。

**F-56の限界**：トークンはブラウザ内に保存されるため、別端末・別ブラウザからは復帰できない。主催者側からの確認URL再発行も持たないため、参加者が別端末で申込を確認する手段はない。これはサーバがないことによる制約である。

### 3-4. セキュリティ・プライバシー

| 項目 | 要件 |
|---|---|
| 申込確認の認可 | `crypto.getRandomValues()` で生成したランダムトークンをURLに含める（`Math.random()` は使用しない） |
| メールアドレスの扱い | 識別（名寄せ）と本人照会にのみ使用する。閲覧の鍵にはしない。送信には使用しない |
| 役割による分離 | 同一データに対し、主催者と参加者で異なる射影を返す（4-3参照） |
| データ保護 | ブラウザ内に平文で保存されるため、実在の個人情報を投入しない。**扱うのはすべて社外の方＝第三者の個人情報**であり、本番運用ではサーバ側での保護が前提となる（F-98） |
| 参加者名簿の閲覧 | イベント横断の個人情報の集積であるため、閲覧前にパスワードを求める（F-101）。**ただしこれは秘匿ではなく操作の抑止**——単一HTMLではパスワードがソースに含まれ、IndexedDB も直接読めるため |

### 3-5. 保守

| 項目 | 要件 |
|---|---|
| スキーマ変更 | `onupgradeneeded` でバージョンを上げ、既存データを保持したままストアを追加できること |
| 開発補助 | データベース初期化とシードデータ投入を必ず備える |
| トランザクション | 複数レコードの更新は原子的に行う。トランザクション内でIndexedDB以外の `await` を挟まない |

## 4. 画面要件

### 4-1. レイアウト

```
┌─────────────────────────────────────────┐
│ ヘッダー（アプリ名 ／ 役割切替 ／ ユーザー）  │
├─────────────────────────────────────────┤
│ ダッシュボード │ イベント │ 参加者 │ 設定 │      │
├─────────────────────────────────────────┤
│              コンテンツ領域               │
└─────────────────────────────────────────┘
```

| 項目 | 方針 |
|---|---|
| 配色 | 青を基調とする。濃紺をヘッダー、青をアクセントとし、他の色は状態表示にのみ使用する |
| 役割切替 | ヘッダーに置く（タブと同列にしない） |
| タブ | **主催者は5つ（ダッシュボード／イベント／通知／参加者／設定）、参加者は3つ（イベントを探す／マイ申込／通知）**（2026-07-29 改訂 / F-108。旧: 主催者4つ）。**中央揃え**で配置する。イベント作成・申込一覧はイベントタブ配下に置く。参加者名簿はイベント横断のため独立させる（2026-07-28 改訂。旧: 3つに固定） |
| 参加者ビュー | 同一シェルを用い、ナビゲーションを簡略化する。1カラム構成とする |
| 画面幅 | **主催者ビューはPC幅のみ。参加者ビューは640px以下に対応する**（F-81 / F-81b。2026-07-29 改訂） |

### 4-2. 画面一覧

| # | 画面 | ビュー | 主な要素 |
|---|---|---|---|
| S-1 | ダッシュボード | 主催者 | 指標カード、申込ヒートマップ（F-103）、要対応リスト、開催カレンダー（月表示 / F-100） |
| S-2 | イベント一覧 | 主催者 | 時期のトグル絞り込み、イベントカード（状態・時期・開催日時・会場・申込バー・準備の進捗バー・要対応の見出し）、新規作成 |
| S-3 | イベント作成・編集 | 主催者 | 入力フォーム、定員・受付期間、公開範囲の選択、画像アップロード、公開前チェック |
| S-4 | イベント詳細 | 主催者 | 上部に状況を固定表示（開始〜終了・申込／定員・残席・タスク進捗）。運営スレッドのサブタブには未読バッジを出す。サブタブは 申込／運営スレッド／運営Q&A／運営タスク／マニュアル／ファイル／お知らせ／告知／概要・編集。サブタブで申込（一覧・検索・チェックイン・CSV）／運営スレッド／運営Q&A／運営タスク／お知らせ／告知（共有URL・投稿文）／概要・編集 |

### 4-3. 役割による見え方の差

| 対象 | 主催者ビュー | 参加者ビュー |
|---|---|---|
| 下書きイベント | 見える | 見えない |
| 限定公開のイベント | 一覧に出る | 一覧に出ない。URL直接指定でのみ閲覧・申込ができる |
| 中止・終了イベント | 見える | 一覧に出ない。URL直接指定時は状態を表示 |
| 定員・残席 | 実数 | 残席または「満席」 |
| 他人の申込 | 全件見える | 見えない |
| 自分の申込 | — | 確認URL経由、またはログイン後の一覧（F-107）から見える |

### 4-4. 画面遷移

```
主催者：S-1 ⇄ S-2 → S-3 → S-4     S-10（参加者名簿・横断）
                     ↓ プレビュー（?preview=）
参加者：S-6 → S-7（入力→確認）→ S-8 → S-9
                                      ↑ ?ticket= から直接復帰
```

### 4-5. 受け入れ確認

以下が最後まで通ることを確認する。

1. シードデータを投入し、表示されること
2. イベントを作成し、画像を添付して下書き保存できること
3. 締切を開催日より後に設定して公開しようとすると、検出されること
4. 修正して公開し、参加者ビューで確認できること（下書きは一覧に出ないこと）
5. 共有URLと投稿文を発行し、X共有ボタンで投稿画面が開くこと
6. 参加者ビューで申込し、完了画面とマイチケットが表示されること
7. ブラウザを再読込してもデータが保持されていること
8. 主催者ビューで申込が一覧に反映され、残席が減っていること
9. 氏名で検索し、チェックインと取り消しができること
10. 申込内容を主催者が修正できること
11. CSVを出力できること
12. 定員まで申込むと、以降は申込できないこと
13. 中止にすると、参加者ビューに状態が表示されること
14. 初期化と再投入ができること
